## 1. 결론

> **개발 가능하다.** Dooray Drive API는 동기화 클라이언트에 필요한 기능(목록·메타·업로드·다운로드·폴더 조작·**증분 변경 추적**)을 모두 제공하며, **실제 API 호출로 핵심 경로를 모두 검증 완료했다.**
>
> 검토 착수 시 세웠던 3대 전제가 모두 해소되었다:
> 1. **IP ACL 접근성 — 통과.** 현재 테스트 망에서 차단 없이 정상 호출 (PoC-01)
> 2. **changes API 동작 — 확인 완료.** 8개 시나리오(생성·수정·개명·폴더생성·이동·폴더개명·휴지통) 전부 관측, hash 알고리즘까지 식별 (PoC-05)
> 3. **대용량 전송 — 통과.** 100MB 왕복 성공, 무결성 검증 통과 (PoC-06)
>
> **다만 공식 문서에 없는 함정 4가지를 실측으로 발견했고, 이를 모르고 구현하면 동기화가 조용히 깨진다:**
>
> | 발견 | 모르고 구현하면 | 참조 |
> |---|---|---|
> | changes API가 **부분 페이지**를 반환 (`size`보다 적게 주면서 뒤에 데이터가 남음) | `len < size`로 종료 → 커서가 과거에 갇혀 **이후 모든 변경을 영구 누락** | §3.1 |
> | **changes는 이벤트 로그가 아니라 "객체별 최신 상태(net) 뷰"** — 객체가 다시 바뀌면 이전 항목은 사라지고 새 revision으로 이동 | 이벤트 스트림으로 오해 → 커서 관리·삭제 해석·중복 판정 로직이 전부 어긋남 | §3.2 |
> | **폴더 개명·이동 시 하위 파일 이벤트가 발생하지 않음** | 하위 파일 전체를 원격 삭제로 오인 → **대량 오삭제** | §3.3 |
> | **이름 변경이 `version`을 증가시키지 않음** | version만 비교 → 개명을 놓침 | §3.3 |
>
> 첫 번째 함정은 실제로 PoC-05 1차 실행을 전 시나리오 실패로 몰았고, 원인을 추적해 규명한 뒤 재실행으로 해결했다. **이 네 가지를 설계에 반영했다는 점이 이번 검토의 가장 큰 실질 성과다.**
>
> *(문서 이력: 본 보고서의 PoC 실측 반영분은 최초 작성 후 독립 재감사를 거쳐 정정되었다. §8 참조.)*

배경: Dooray는 데스크톱용 드라이브 동기화 앱을 제공하지만 [공식 FAQ](https://helpdesk.dooray.com/share/pages/9wWo-xwiR66BO5LGshgVTg/2909486247933660381)에 **"공공기관은 현재 지원하지 않습니다"**라고 명시되어 있어, 공공기관에서는 자체 개발 외 대안이 없다.

**기반 사양**
- 엔드포인트: 공공 클라우드 `https://api.gov-dooray.com` / 공공 업무망 `https://api.gov-dooray.co.kr`
- 인증: 개인 API 토큰, `Authorization: dooray-api {TOKEN}` 헤더. 계정과 동일 권한·동일 ACL(IP/User) 적용. TLS 1.2+
- Rate limit: Token Bucket, `X-RateLimit-*` 응답 헤더 제공(수치 비공개·변동 가능), 초과 시 429
- 파일 크기: 웹 기준 1개당 Basic 500MB / Business 이상 10GB. **청크·이어올리기 업로드 미제공**
- 서버 변경 푸시(웹훅) 미제공 → 자동 동기화는 폴링 (공식 민간용 앱도 10분 주기 폴링)

**미지원/제약 사항 정리**
- 이어올리기(resumable) 업로드 없음 → 전송 실패 시 전체 재전송
- 파일 잠금 API 없음 → 동시 편집 충돌은 클라이언트 정책으로 해소
- 영구삭제는 휴지통 내 파일 한정(`DELETE`) → 동기화 도구에서는 사용하지 않음(안전 정책)

### 3.1 핵심 발견 ①: changes API는 **부분 페이지**를 반환한다 (동기화 정확성의 급소)

1차 PoC-05 실행이 전부 실패했고, 원인을 추적한 결과 **changes API의 페이지네이션이 일반적인 관례와 다르다**는 사실을 발견했다.

- 요청 `size`보다 **적은 개수를 반환하면서도 뒤에 데이터가 남아 있는** 경우가 있다. 보존된 가장 깨끗한 증거: `size=5` 요청에 **3건만** 반환됐으나 그 뒤에 1.4만 건 이상이 존재했다(`05_changes.json:param_probe.revision` — count 3). 1차 실행에서도 첫 조회가 101건에서 끊겼다(당시 요청 size는 로그에 미보존, 소스 기준 200으로 추정).
- 즉 **`len(items) < size`를 "마지막 페이지"의 종료 조건으로 사용하면 안 된다.** 이 조건을 쓰면 커서가 과거 어느 지점에 멈춰버리고, 그 이후의 모든 변경을 영원히 놓친다(1차 실행에서 실제로 발생: 커서가 1만여 건 백로그의 첫 페이지 끝인 revision 3365에 갇혀, 이후 폴링이 과거 이력만 1 revision씩 기어감).
- **올바른 종료 조건은 "0건 응답(빈 배열)"뿐이다.** changes 응답 최상위 키는 `header`, `result` 둘뿐으로 **`totalCount`가 없어**(PoC-09 원시 envelope 보존) 총량을 미리 알 수 없다.

**대조 확인 (PoC-09 통제 실험)**: 파일 목록 API(`GET /drives/{d}/files`)는 정상이다 — 자식 7개 폴더에서 `size=2/3/5/7/12` 전부 요청 수만큼 정확히 반환했고 `totalCount=7`도 일치했다(`09_net_semantics.json:listing_pagination_strict`). 즉 **부분 페이지 함정은 changes API에만 존재**한다.

> **설계 반영(필수)**: `core/remote.py`의 델타 수집 루프는 반드시 **빈 배열을 받을 때까지** 페이징한다. 커서는 마지막 항목의 `(revision, file.id)` 쌍으로 전진시키고, 커서가 전진하지 않으면 무한루프 방지를 위해 중단한다. 이 규칙을 코드 주석과 단위 테스트로 고정한다. — 이 한 줄을 놓치면 자동 동기화가 조용히 변경을 누락한다(가장 위험한 실패 유형).

### 3.2 핵심 발견 ②: changes는 이벤트 로그가 아니라 "객체별 최신 상태(net) 뷰"다

**판별 실험 1 (재조회)**: PoC-05 시나리오 직전 커서(rev 17514)에서 재조회하자, 시나리오 중 관측됐던 `updated` 6건(17515~17520)이 **사라지고** 최종 상태 4건만 남았다 — 파일 톰스톤(17521), **부모 폴더 `_poc_sandbox`의 updated(17522)**, 폴더 톰스톤(17522), 마커 톰스톤(17523).

**판별 실험 2 (coalescing, PoC-09 통제 실험)**: 폴링 없이 파일 생성→내용 수정→이름 변경을 연속 수행한 뒤 단일 조회 → 대상 파일에 대한 항목이 **정확히 1건**(최종 이름, version 1, 최종 hash)만 반환됐다(`09_net_semantics.json:coalescing`).

즉 changes의 항목은 영구 이벤트가 아니라 **객체당 1건의 최신 상태**이며, 객체가 다시 변경되면 항목이 새 revision으로 **이동**하고 이전 항목은 피드에서 소멸한다. 이 모델은 그동안의 모든 이상 관측을 일관되게 설명한다:

- 파일 12개를 생성 후 곧바로 휴지통 이동(24작업, revision 24개 소비)했을 때 **12건**(파일당 deleted 1건)만 도착
- 과거 전량 스캔에서 "생성 후 휴지통까지 간" 테스트 파일들이 이름으로 검색되지 않음(null-name 톰스톤만 잔존)
- 동일 revision(17522)에 항목 2건 공존 → **`(revision, fileId)` 복합 커서가 필수인 이유**

**반영 지연**: 커서가 tip에 있으면 각 작업이 **1~2초 내** 감지됐다(8개 시나리오 전부). 실질적 인덱싱 지연은 없다.

> **정정 기록**: 본 보고서 초판은 이 절에서 "커서가 tip인데 0건 반환 후 다음 조회에 몰아서 도착하는 현상"을 API 특성으로 기술했으나, 재감사 결과 **해당 0건 조회는 이벤트 발생 이전 시점**이었음이 타임라인 재구성으로 확인되어 철회한다. 또한 초판의 "반영 지연 30~90초" 추정도 부분 페이지 버그(§3.1)로 인한 오측이었다.

> **설계 반영**: (a) 항목은 커서 앞으로만 이동하므로 **객체의 최종 상태는 구조적으로 유실 불가** — Google Drive changes와 같은 계열의 설계로, 동기화에 유리. (b) 한 폴링 창에서 생성+삭제된 파일은 **"모르는 file_id의 deleted 톰스톤"** 으로만 보인다 → 클라이언트는 이를 정상 케이스로 무시. (c) 중간 상태(개명 전 이름 등)는 관측 불가할 수 있으므로 **changes 항목의 name/path를 항상 정본으로 수용**. (d) 자기가 방금 수행한 작업은 API 응답값으로 로컬 DB를 즉시 갱신하고, changes는 웹 UI·타 클라이언트발 **외부 변경** 감지용으로 사용.

### 3.3 시나리오별 changes 표현 (실측 확정 — 동기화 판정 로직의 근거)

> **읽는 법 (§3.2의 net-뷰 전제)**: 아래 표는 **커서가 tip에 있는 상태에서 작업 1개씩 수행·조회**했을 때 관측된 항목이다. 항목은 영구 이벤트가 아니므로, 한 폴링 창에서 같은 객체에 여러 작업이 일어나면 **최종 상태 1건**으로 합쳐진다(예: 생성+수정+개명 = updated 1건, 생성+휴지통 = deleted 1건 — PoC-09 실증).

| 작업 | changeType | `file.type` | `name` | `path` | `version` | `hash` |
|---|---|---|---|---|---|---|
| 파일 생성 | `updated` | file | 새 이름 | **부모 폴더 경로** | 0 | MD5 |
| 내용 수정(PUT 새 버전) | `updated` | file | 동일 | 동일 | **1로 증가** | **변경됨** |
| 파일 이름 변경 | `updated` | file | **새 이름** | 동일 | **증가하지 않음(유지)** | 동일 |
| 폴더 생성 | `updated` | folder | 새 이름 | 부모 경로 | 0 | `null` |
| 파일 이동 | `updated` | file | 동일 | **새 부모 경로** | 유지 | 동일 |
| **폴더 이름 변경** | `updated` | folder | 새 이름 | 부모 경로 | 0 | `null` — **하위 파일 이벤트는 발생하지 않음** |
| 휴지통 이동(파일/폴더) | `deleted` | file/folder | **`null`** | **`null`** | `null` | `null` |

**여기서 파생되는 필수 설계 규칙 4가지:**

1. **`path`는 파일명을 제외한 부모 폴더 경로다.** 전체 경로 = `path` + `/` + `name` (예: `name='poc05_A.bin'`, `path='/_poc_sandbox'`).
2. **이름 변경은 `version`을 올리지 않는다.** version만 비교하면 개명을 놓친다 → 변경 감지는 **`(version, name, path)` 조합**으로 판정한다.
3. **폴더 개명·이동 시 하위 파일 이벤트가 없다 (R8이 현실로 확인됨).** 폴더 `updated` 수신 시 **해당 폴더 하위 트리를 목록 API로 재열람**해 자손 경로를 갱신해야 한다. 빠뜨리면 하위 파일 전체가 "원격에서 사라진 것"처럼 보여 **대량 오삭제** 위험이 생긴다.
4. **`deleted` 항목에는 `id`·`type`·`revision`만 있고 name/path/version/hash/size는 전부 `null`이다.** 경로를 알려면 로컬 상태 DB에서 `file_id`로 역참조해야 한다 → **상태 DB는 필수**이며, DB 손상은 곧 삭제 해석 불능이므로 백업·복구 설계가 중요하다.

### 3.4 업로드 시 이름 충돌은 서버가 409로 거부한다 (안전 측면에서는 유리)

같은 폴더에 같은 이름으로 `POST` 하면 시간 간격·파일 내용과 무관하게 **HTTP 409 "Duplicate request."** 로 거부된다(실측 확인). 서버가 자동 개명하거나 조용히 덮어쓰지 않는다.

> **설계 반영**: 업로드 전 대상 폴더에서 동일 이름 존재 여부를 확인해 **존재하면 `PUT ?media=raw`(새 버전), 없으면 `POST`(신규)** 로 분기한다. 409를 받으면 "경쟁 상태에서 다른 주체가 같은 이름을 먼저 만들었다"는 신호이므로, 재조회 후 버전 업데이트 또는 충돌 처리로 전환한다. 서버가 임의로 덮어쓰지 않는 점은 안전성 측면에서 유리하다.

### 3.5 changes 전량 스캔 규모 — "이력"이 아니라 "드라이브 보유 객체 수"다

`latestRevision=0`부터 live tip까지 전량 스캔 결과는 **총 14,317건 / 75페이지**(updated 13,993 / deleted 324)였다. §3.2의 net-뷰 의미론에 따라 이 수치의 올바른 해석은 "과거 변경 이력 1.4만 건"이 아니라 **"이 드라이브가 보유한 살아있는 객체 약 13,993개 + 삭제 톰스톤 324개"** 다. (초판의 "과거 대량 재인덱싱 이력" 추정은 철회.)

> **설계 반영**: 초기 스캔은 changes 전량 순회 대신 **목록 API 전체 순회로 현재 상태를 구축**하고, changes 커서는 live tip까지 전진시켜 놓기만 한다. 전량 스캔은 드라이브 규모에 비례해 느리므로(아래 §3.6) 초기화 시 1회로 한정한다.

### 3.6 changes 전량 스캔의 소요 시간 (정정 반영)

changes 75페이지(14,317건) 연속 조회에 **약 6분(요청당 평균 ~4.8초)** 이 걸렸다.

> **정정 기록**: 초판은 이 소요를 "429 백오프 반복" 때문이라고 기술했으나, 재감사 결과 **전 로그에 429 기록이 0건**이었다(429는 클라이언트가 자동 로깅함). burst=20·replenish=5/s 기준 75요청의 이론 소요는 ~15초에 불과하므로, 병목은 rate limit이 아니라 **changes 쿼리 자체의 서버 응답 지연**이다.

> **설계 반영**: (a) rate limit 헤더 실측값은 **burst=20, replenish=5/s**(전 실행에서 일관) — 응답 헤더 기반 선제 감속(pacing)은 여전히 구현한다(`X-RateLimit-Remaining` 임계 이하 시 요청 간격 확대). (b) 다만 초기 changes 전량 스캔이 느린 원인은 서버 측이므로, **초기화 경로에서 changes 전량 스캔 자체를 피하는 §3.5의 설계**(목록 API로 상태 구축)가 근본 대책이다. (c) 전송 병렬도는 1(순차) 유지.

### 3.7 그 밖의 실측 확정 사항 (PoC-08·09)

1. **서버가 파일명을 정규화한다 — 왕복 불일치 3건**: 앞 공백 제거, 뒤 공백 제거, `"`→`%22` 치환. 이 중 **앞 공백 제거가 동기화에 가장 위험**하다: ` 보고서.hwp`는 Windows에서 합법적 이름이므로, 그대로 업로드하면 서버에는 `보고서.hwp`로 저장되고, 다음 동기화에서 로컬 ` 보고서.hwp`와 원격 `보고서.hwp`가 서로 다른 파일로 보여 **매 주기 재업로드/재다운로드 루프**가 생길 수 있다.
   → **설계 규칙: 업로드 응답의 서버 저장명을 정본으로 상태 DB에 기록**하고, 로컬명과 서버명이 다르면 매핑을 유지하거나 로컬명을 서버명에 맞춰 정규화(사용자 통지)한다.
2. **폴더 휴지통 이동은 하위 트리에 재귀 적용된다**: 부모 폴더를 휴지통으로 보낸 뒤 그 안의 파일에 move를 호출하면 실패한다. 이때 오류가 **HTTP 200 + `resultCode: -15700100` ("No access authority")** 로 반환된다(PoC-09에서 8건 관측) — **HTTP 상태코드만으로 성공을 판정하면 안 된다**는 공식 문서 경고의 실증 사례. 클라이언트는 반드시 `header.isSuccessful`/`resultCode`를 검사해야 한다(현 PoC 공통 코드는 이미 준수).
3. **부모 폴더의 updated 항목이 나타나는 조건은 작업 종류에 따라 다르다**: 자식 폴더 휴지통 이동 시에는 부모의 updated가 관측됐으나(§3.2 실험 1), 자식 파일 생성 시에는 나타나지 않았다(PoC-09). 조건이 완전히 규명되지 않았으므로, 클라이언트는 **예기치 않은 폴더 updated 항목을 노이즈로 안전 처리**(하위 재열람 규칙과 자연 합치)한다.
4. **확장자 없는 예약어 `CON`도 서버는 수용**한다(저장명 그대로 `CON`). Windows 로컬 저장 가능성과는 별개 문제이므로, 원격에 존재하는 Windows 비호환 이름은 기존 unsyncable 정책으로 처리한다.

```
├─ api/      # DoorayClient(수동 307, 429 백오프, fail-stop) + DriveAPI
│            #   ※ 영구삭제(DELETE) 메서드는 의도적으로 미구현 — 코드 수준 차단
├─ core/     # scanner(로컬) / remote(델타+전체재조정) / differ(3-way) / planner / executor / journal
├─ store/    # SQLite WAL: files(마지막 동기화 상태) + journal(크래시 복구) + conflicts + meta(revision 커서)
├─ cli/      # typer: init/status/sync/pull/push/resolve/watch/doctor — 코어와 완전 분리(부서 확장 대비)
├─ daemon/   # watchdog 디바운스(5초) + changes 폴링(120초) + 일일 전체 재조정
└─ util/     # NFC 정규화, \\?\ 긴 경로, 예약어 검사, 스트리밍 해시, 단일 인스턴스 잠금
```

**PoC 실측이 설계에 강제한 규칙 (반드시 코드에 고정)**

| 실측 발견 | 코드에 고정할 규칙 |
|---|---|
| changes API 부분 페이지 (§3.1) | 델타 수집은 **0건 응답까지만** 종료. `len < size` 금지. 단위 테스트로 회귀 방지 |
| **changes = 객체별 net 상태 뷰** (§3.2, PoC-09 확정) | `(revision, fileId)` 복합 커서. 미지 id의 deleted는 정상 무시. changes 항목의 name/path를 정본 수용. 자기 작업은 API 응답값으로 DB 즉시 갱신(반영 지연은 1~2초로 사실상 없음) |
| 목록 API는 `totalCount` 제공·엄격 페이지네이션 (§3.1, PoC-09 확정) | 초기 스캔·전체 재조정은 changes가 아닌 **목록 API**로 수행 |
| 같은 이름 POST → 409 (§3.4, PoC-09 보존) | 업로드 전 이름 존재 확인 → 있으면 `PUT`(새 버전), 없으면 `POST`. 409는 경쟁 상태 신호로 처리 |
| 끝 점(`.`) 이름은 Windows 일반 경로에서 잘림 (PoC-08) | 모든 로컬 파일 IO에 `\\?\` 접두 상시 적용 |
| **서버가 파일명 앞뒤 공백 절삭** (§3.7) | 업로드 응답의 **서버 저장명을 정본으로 DB 기록** — 재전송 루프 방지 |
| 목록 응답에 hash 없음 (PoC-02) | 목록 기반 재조정에서는 `(version, name, path, size)`로 판정. hash는 changes 수신 시 활용 |
| **hash = MD5(hex)** (PoC-05, 2회 교차검증) | 내용 동일성 비교에 MD5 사용 → 타임스탬프만 바뀐 파일의 **가짜 충돌 제거** |
| **이름 변경은 version 불변** (§3.3) | 변경 감지 키를 `(version, name, path)` 조합으로 구성 |
| **폴더 개명 시 하위 이벤트 없음** (§3.3) | 폴더 `updated` 수신 → **하위 트리 목록 재열람 필수** |
| **`deleted`는 id·type·revision만 제공** (§3.3) | `file_id` 역참조용 상태 DB 필수 + DB 백업/복구 설계 |
| **오류가 HTTP 200 + 음수 resultCode로 반환 가능** (§3.7) | 모든 응답에서 `header.isSuccessful`/`resultCode` 검사 — HTTP 상태만으로 성공 판정 금지 |

**안전 장치 핵심**
- 원자적 다운로드: 같은 볼륨 임시파일 → 검증 → `os.replace()`. 실패해도 원본 무손상
- 교체 직전 재검사: 대상 파일이 스캔 시점과 다르면 중단 → 충돌 처리 (편집 경합 방지)
- 충돌 시 양쪽 보존: `이름 (충돌 YYYY-MM-DD HHMM).ext` 사본 생성
- 삭제 전파: 원격은 휴지통 이동만, 로컬은 Windows 휴지통만. **초기 기본값은 삭제 미전파**, 대량 삭제(50개/20% 초과) 시 자동 중단
- 작업 저널(planned→…→committed)로 크래시 후 무손실 재개, dry-run 모드, 단일 인스턴스 잠금

**수동/자동 동기화**
- 수동: `dsync sync/pull/push/status/resolve` CLI
- 자동: `dsync watch` — 파일시스템 감시(디바운스) + changes 폴링 + 일일 전체 재조정. Windows 작업 스케줄러 등록으로 로그인 시 자동 시작

## 6. 로드맵 및 공수 (1인 개발 기준)

| 단계 | 내용 | 완료 기준 | 공수 |
|---|---|---|---|
| M0 | PoC 8종 실행 + 본 보고서 확정 | PoC-01·05 green | 3~5일 |
| M1 | 수동 단방향 (push/pull, 덮어쓰기 금지, dry-run) | 실 업무 폴더 2주 무사고 | 1~1.5주 |
| M2 | 양방향 + 상태 DB + 충돌 처리 + 저널 복구 | 전송 중 강제종료 후 무손실 수렴 | 2~3주 |
| M3 | 자동 데몬 (watch) + rate-limit 스케줄러 | 5영업일 무인 운용 | 1~2주 |
| M4 | 하드닝 + 부서 확장 준비 (exe 패키징 등) | 안전성 체크리스트 통과 | 2주+ |

## 7. 기관 확인 필요사항 (행정 절차)

1. **IP ACL 정책**: 기관 Dooray 관리자에게 API 접근 IP 제한 여부 확인 (자택 IP에서 사용 가능해야 함)
2. **서비스 플랜**: 파일 1개당 업로드 한도 확인 (Basic 500MB / Business+ 10GB)
3. **보안 내규**: 개인 PC에 업무 파일 동기화·저장이 기관 보안 정책상 허용되는지 (재택근무 규정 확인)
4. **토큰 정책**: 개인 API 토큰 사용에 대한 기관 방침 (만료 주기, 발급 제한 여부)
