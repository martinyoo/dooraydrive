# AI 에이전트 운영 교훈 (AgentOps)

Dooray Drive 동기화 도구 개발 세션(2026-07-29 ~ 08-01)에서 **실제로 발생한 사고와 오진**을 기록한 것이다.
일반론이 아니라 이 세션에서 증거로 확인된 것만 담았다.

- 대상 작업: 타당성 검토 → PoC 9종 → M1 구현(18파일) → 실계정 파일럿
- 참여: Fable 5 / Sonnet 5 / Opus 5 (세션 중 모델 4회 전환), 서브에이전트·워크플로 약 40개

---

## 1. 실행 환경 경계를 확인하기 전에 파괴적 명령을 쓰지 말 것

**사고**: 원인 재현을 위해 `rm -rf "$LOCALAPPDATA/dooray-sync/swstat"`를 실행했는데,
이것이 **사용자 PC의 상태 DB를 실제로 삭제**했다.

**왜 예측하지 못했나**: 경계가 경로마다 달랐다.

| 경로 | 실제 동작 |
|---|---|
| 작업 폴더 `C:\drive\dev\dooraydrive` | 공유 — 어시스턴트가 만든 파일을 사용자가 실행 가능 |
| `%APPDATA%` | **분리** — 어시스턴트가 만든 설정이 사용자 PC에 없었음 |
| `%LOCALAPPDATA%` | **공유** — 어시스턴트의 삭제가 사용자에게 반영됨 |

"내 쪽에서 파일이 보인다"는 것이 사용자 PC에도 있다는 증거가 되지 못했고,
그 반대(내가 지우면 사용자 것도 지워진다)도 성립했다.

**규칙**
- 작업 디렉터리 **밖**에는 쓰기·삭제 명령을 실행하지 않는다. 사용자가 실행할 명령을 안내한다.
- 재현 실험이 필요하면 환경변수로 경로를 작업 폴더 하위에 격리한다
  (예: `DOORAY_SYNC_STATE_DIR=<project>\.dbg\state`).
- 사용자 PC의 상태는 **사용자가 직접 실행한 명령의 출력**으로만 판단한다.

---

## 2. 재현되지 않는 문제는 추측하지 말고 진단을 코드에 심어라

**증상**: `설정 파일이 없습니다` — 파일은 실재하는데 프로그램이 없다고 함. 어시스턴트 환경에서는 재현 불가.

**오진 3회** (각각 근거를 들었으나 전부 틀림)

| # | 가설 | 반증 |
|---|---|---|
| 1 | 백신이 파일을 잠가 `os.path.exists`가 False 반환 | 결정적으로 재현됨 — 일시적 현상 아님 |
| 2 | Microsoft Store Python의 AppData 가상화 | Store Python 미설치 |
| 3 | 관리자 권한 상승으로 다른 계정 프로필 참조 | `관리자 권한: False`, 동일 계정 |

**해결**: 오류 메시지에 진단 정보(경로·존재 여부·실행 계정·폴더 내용·파이썬 경로)를 넣자
**한 번의 왕복으로** 원인이 잡혔다 — `APPDATA 총 항목 수: 17 vs 16`.

**규칙**
- 재현 안 되는 문제에 가설을 3개 이상 세우고 있다면, 그 시점에 **진단 출력을 만드는 쪽으로 전환**한다.
- 오류 메시지는 "무엇이 잘못됐다"가 아니라 **"내가 무엇을 어디서 보았는지"**를 담는다.
- 사용자에게 왕복 요청을 할 거면, 한 번에 판별 가능한 정보를 모아서 요청한다.

---

## 3. "완료" 보고 전에 사용자 측 증거를 확인하라

**사고**: "프로파일 4개 설정 완료"라고 보고했으나 **사용자 PC에는 아무것도 만들어지지 않았다**(§1 참조).
사용자는 그 말을 믿고 `push`를 시도했다가 실패했다.

**규칙**
- 어시스턴트 환경에서만 확인한 것은 "확인됨"이 아니다. **무엇을 어떻게 검증했는지 함께 밝힌다.**
- 사용자 환경에 대한 변경은 "내가 했다"가 아니라 "이 명령을 실행하시면 됩니다"로 전달한다.

---

## 4. 검증되지 않은 인과를 실측처럼 쓰지 말 것

**사고**: 검토보고서에 *"75페이지 스캔에서 429 백오프가 반복 발생해 6분이 걸렸다"*고 적었다.
**로그에 429 기록은 0건**이었다(클라이언트가 429를 자동 로깅하는데도). 실제 원인은 서버 응답 지연이었고,
산술로도 맞지 않았다(75요청 이론치 약 15초 vs 실제 359초).

독립 재감사로 **불일치 8건·근거부족 7건**이 나왔다. 그중 일부는 세션 중 실측했으나
**stdout으로만 출력하고 파일에 남기지 않아** 근거를 재현할 수 없었던 것들이다.

**규칙**
- 측정하지 않은 인과는 "추정"이라고 쓰거나 쓰지 않는다.
- 실측 결과는 **파일에 보존**한다(stdout은 사라진다). 이후 모든 프로브는 결과 JSON에 기록하도록 공정을 바꿨다.
- 자기 산출물은 **다른 관점으로 재감사**한다. 이 세션에서는 다른 모델이 원시 증거와 전수 대조해 잡아냈다.

## 5. 게이트는 "존재"가 아니라 "의미"를 검사하라

같은 실수를 두 번 했다.

**1차**: `SETUP.ps1`이 상태 DB **파일 존재**만 확인 → 빈 DB가 통과 →
그 상태로 push하면 원격에 이미 있는 파일을 신규로 오인해 **중복 업로드**(swstat 7건, spri2025 258건).
다행히 사용자가 `--dry-run`만 실행해 사고는 없었다.

**2차**: 이를 고쳐 **레코드 건수 > 0**으로 바꿨더니, 이번엔 정상적으로 비어 있는 신규 원격 폴더(spri2026)에서
오탐으로 막혔다. 검사하려던 진짜 명제는 "원격 스캔이 실제로 완료되었는가"이므로
`META_LAST_FULL_SCAN` 기록 여부를 봐야 한다.

**규칙**
- 게이트를 만들 때 **검사하려는 불변식을 문장으로 먼저 쓰고**, 그것을 직접 표현하는 값을 고른다.
- 프록시 지표(파일 존재, 건수)는 양방향 오류를 낸다 — 통과시켜선 안 될 것을 통과시키거나 그 반대.

> **2026-08-01 수정 완료.** `SETUP.ps1` 2-1 게이트를 `META_LAST_FULL_SCAN` 기준으로 교체했다.
> 양방향 검증함 — 스캔 완료·0건은 통과, 스캔 미완료 DB는 차단(`DOORAY_SYNC_STATE_DIR`로 격리 생성).
> 이 항목이 **문서에는 적혀 있었으나 코드는 고쳐지지 않은 채** 다음 세션으로 넘어갔다. §10 참조.

## 6. 병렬 구현 전에 인터페이스를 계약으로 고정하라

M1 구현은 서브에이전트 다수가 모듈을 나눠 동시에 작성했다. 성공 요인은
**`docs/모듈규약.md`를 먼저 확정**한 것이다 — 전 모듈의 시그니처·타입·예외·금지사항을 단일 진실 소스로 두고,
각 에이전트가 그것만 신뢰하게 했다.

결과: 18개 파일이 첫 통합에서 **임포트 오류 0건**으로 맞물렸다.

**규칙**
- 병렬 작성 전 계약 문서를 만든다. 계약이 없으면 통합 비용이 병렬 이득을 넘는다.
- 계약 문서에 **금지사항**(하지 말아야 할 것) 절을 둔다. 긍정 명세만으로는 위험한 구현을 막지 못한다.

## 7. 적대적 검증은 실제로 데이터 손실을 막는다

4관점(금지사항·계약준수·런타임·안전성) 리뷰 후 각 지적을 **반박하는** 검증 단계를 거쳐
**확정 결함 11건**(critical 3)을 얻었다. 전부 데이터 손실 계열이었다.

| 결함 | 방치했다면 |
|---|---|
| init 후 기준선이 비어 첫 push가 원격을 로컬로 덮어씀 | 원격 최신본 소실 |
| NFC 정규화 경로로 NFD 파일 접근 불가 | 해당 파일 영구 미백업(조용히) |
| 재-stat이 전송 **시작 전**에만 수행 | 다운로드 중 저장한 편집 소실 |

**규칙**
- "찾아라"만으로는 부족하다. 찾은 것을 **반박하게** 해야 오탐이 걸러지고 진짜만 남는다.
- 검증 관점에 **"이 코드가 데이터를 잃을 수 있는 경로"**를 반드시 넣는다.

---

## 8. 실계정 테스트가 잡는 것은 코드 리뷰가 못 잡는다

정적 검증을 모두 통과한 뒤 실제 계정에서 돌리자 두 가지가 나왔다.

- **네트워크 전송 계층 오류**(`RemoteProtocolError`)가 실제로 발생 — 재시도가 없어 init 전체가 실패했다.
  코드 리뷰로는 "일어날 수도 있다"까지만 알 수 있었다.
- **원격 순회 비용이 폴더 수에 비례**(폴더당 약 0.4초) — 드라이브 전체 지정 시 1시간 초과.
  실사용자는 업무 폴더 하나만 원한다는 사실이 실행 중에 드러나 `--remote-path` 옵션을 추가했다.

**규칙**: "완료"는 실제 대상에서 한 번 돌려본 뒤에 선언한다.

## 10. 교훈을 적었으면 같은 커밋에서 코드도 고쳐라

**사고**: 이 문서 §5에 게이트 오탐(spri2026)과 해법(`META_LAST_FULL_SCAN`)이 **이미 적혀 있었는데**
`SETUP.ps1`은 `count_files > 0`인 채로 커밋되어 있었다. 그래서 이번 세션이 같은 지점에서 다시 막혔고,
원인 진단을 처음부터 되풀이했다.

**왜 놓쳤나**: 교훈 문서에 쓰는 행위가 "처리했다"는 느낌을 준다. 문서는 지식을 남기지만
**동작을 바꾸지 않는다**. 게다가 `현재상태.md`는 여전히 반대 내용(§11)을 말하고 있어,
두 문서가 충돌한 채 방치됐다.

**규칙**
- 결함을 교훈 문서에 적을 때는 **코드 수정 여부를 같은 항목에 명시**한다 — "수정 완료" 또는 "미수정(사유)".
- 미수정으로 남긴다면 `현재상태.md`의 **미해결 작업 표에도 올린다**. 교훈 문서는 읽히지 않을 수 있다.
- 세션 시작 시 교훈 문서의 "미수정" 항목을 먼저 확인한다.

## 11. 인수인계 문서는 원인을 단정하지 말고 판별법을 써라

**증상**: `현재상태.md`에 *"SETUP.ps1이 멈추면 그 프로파일의 `init`이 실패한 것이다"*라고 적혀 있어,
실제로는 init이 성공했는데도 init 실패를 먼저 의심했다.

**원인**: 문서가 **증상**이 아니라 **원인**을 단정했다. 읽는 쪽에서는 검증 없이 통과시키는 전제가 된다.
§5의 진짜 원인이 이미 밝혀진 뒤에도 이 문장은 갱신되지 않았다.

**규칙**
- "멈추면 X가 실패한 것이다"가 아니라 **"멈추면 `python diag.py <프로파일>`로 스캔 시각과 기록 건수를 확인하라"**로 쓴다.
- 이미 적힌 원인 단정은 근거를 재확인하기 전까지 **가설로만** 취급한다.

## 12. "대상 0건"과 "일치 0건"은 다르다

**오진**: `reconcile -p workenv`의 `대조 대상 0건`을 보고
"로컬·원격에 겹치는 파일이 하나도 없다"고 사용자에게 잘못 보고했다.

**실제**: "대조 대상"은 *기준선이 없는* 교집합만 센다. workenv는 26건이 겹치되
**이미 기준선이 잡혀 있어서** 대상이 아니었다. 0의 의미가 "해당 없음"인데 "일치 없음"으로 읽었다.

**규칙**: 0을 근거로 결론을 말하기 전에 그 0이 **무엇을 세는 값인지** 확인한다.
여기서는 `diag.py`의 `키 교집합`이 실제 겹침 수이고 `reconcile 대상`은 그중 미해결분이다 — 둘을 같이 봐야 한다.

---

## 13. 잘린 출력은 산술로 교차검증한다

**증상**: `push --dry-run` 출력이 `... 외 297건`으로 잘려 총계를 알 수 없었다.
그대로 두면 계획에 누락·중복이 있어도 모른 채 3.18GB를 올리게 된다.

**규칙**: 화면에 보이는 것이 전부가 아니다. 독립적으로 계산해 대조한다.
spri2025는 `로컬 797건 − synced 258건 − 기존 원격폴더 42건 = 497건`이 계획 건수와 정확히 일치해
누락·중복 없음을 확인한 뒤 실행했다. 업로드 용량과 최대 파일 크기도 별도로 합산해 둔다.

---

## 14. 문서의 수치는 실행 직전에 전수 재측정한다

**증상**: `현재상태.md`는 플랜 한도(500MB) 초과 파일을 **1건**(spri2026의 589.5MB 동영상)으로 적고 있었다.
실제 스캔 결과 workenv에 **876.7MB**(`연구용sw/stata17/setupstata17.exe`)가 더 있었다 — 문서에 적힌 것보다 크다.

**원인**: 리스크 목록은 작성 시점의 표본이다. 이후 로컬 폴더가 바뀌면 갱신되지 않는다.

**규칙**: 한도·용량처럼 **실패를 유발하는 값**은 실행 직전에 전수 스캔으로 다시 센다.
문서는 "무엇을 봐야 하는지"의 단서로 쓰고, **수치의 근거로는 쓰지 않는다**.

## 15. 되돌리기 어려운 작업: 수치 제시 → 건별 승인 → 사후 검증

M1에는 삭제 경로가 없다. 잘못 올리면 수작업으로 지워야 한다(spri2025는 442개).

**실행 전** — 다음을 제시하고 승인받는다.

| 제시할 값 | spri2025 실제 |
|---|---|
| 신규 / 덮어쓰기 / 삭제 | 442건 / **0건** / **0건** |
| 용량 | 3.18 GB |
| 최대 파일 크기 (플랜 한도 대비) | 362.1MB (한도 이내) |
| 문서상 미확인 선결 항목 | 드라이브 여유 용량 미확인 |

승인은 **그 작업 하나에만** 유효하다 — spri2025 승인으로 나머지 프로파일까지 올리지 않는다.

**실행 후** — "실패 0건" 출력으로 끝내지 않는다.

| 확인 | 기대값 |
|---|---|
| `python diag.py <프로파일>` | `local_md5 보유` = `로컬 항목(파일만)`, `reconcile 대상 0` |
| `push --dry-run` 재실행 | `변경 없음` |

spri2025는 base 300 → 797(계획 497건과 정확히 일치), 로컬 700파일 전부 md5 보유,
재-dry-run `변경 없음`으로 확인했다.

## 16. 검증하려고 파괴적 재실행을 하지 않는다

**상황**: 게이트 수정을 검증하려면 `SETUP.ps1`을 다시 돌리는 게 자연스러워 보였다.
그러나 그 안의 `init --force`가 방금 push로 채운 spri2025 기준선(700건)을 건드린다.
검증 비용이 검증 대상보다 크다.

**규칙**: 수정한 **블록만 떼어** 실행해 검증하고, 상태를 만들어야 하는 음성 테스트는
`DOORAY_SYNC_CONFIG_DIR` / `DOORAY_SYNC_STATE_DIR`로 프로젝트 하위에 격리한다(`.dbg/`는 gitignore 대상).
검증용 디렉터리는 끝나고 지운다.

## 17. 한글 `.ps1` 편집 후에는 인코딩·구문을 확인한다

`SETUP.ps1`은 UTF-8 **with BOM**이다. BOM이 사라지면 PowerShell이 CP949로 읽어 한글이 깨진다.
편집 후 세 가지를 확인한다.

1. BOM 유지 — 첫 3바이트가 `EF BB BF`
2. 구문 — `[System.Management.Automation.Language.Parser]::ParseFile()` 오류 0건
3. 한글 렌더링 — `Get-Content -Encoding UTF8`로 수정 구간을 다시 읽어 확인

깨졌다면 편집 도구 대신 `Set-Content -Encoding utf8`로 재작성한다.
