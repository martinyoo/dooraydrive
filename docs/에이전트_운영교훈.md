# AI 에이전트 운영 교훈 (AgentOps)

Dooray Drive 동기화 도구 개발 세션(2026-07-29 ~ 08-01)에서 **실제로 발생한 사고와 오진**을 기록한 것이다.
일반론이 아니라 이 세션에서 증거로 확인된 것만 담았다.

- 대상 작업: 타당성 검토 → PoC 9종 → M1 구현(18파일) → 실계정 파일럿
- 참여: Fable 5 / Sonnet 5 / Opus 5 (세션 중 모델 4회 전환), 서브에이전트·워크플로 약 40개

---

## 1. 실행 환경 경계를 확인하기 전에 파괴적 명령을 쓰지 말 것

**사고**: 원인 재현을 위해 `rm -rf "$LOCALAPPDATA/dooray-sync/swstat"`를 실행했는데,
이것이 **사용자 PC의 상태 DB를 실제로 삭제**했다.

**왜 예측하지 못했나**: 경계가 경로마다 달랐다.

| 경로 | 실제 동작 |
|---|---|
| 작업 폴더 `C:\drive\dev\dooraydrive` | 공유 — 어시스턴트가 만든 파일을 사용자가 실행 가능 |
| `%APPDATA%` | **분리** — 어시스턴트가 만든 설정이 사용자 PC에 없었음 |
| `%LOCALAPPDATA%` | **공유** — 어시스턴트의 삭제가 사용자에게 반영됨 |

"내 쪽에서 파일이 보인다"는 것이 사용자 PC에도 있다는 증거가 되지 못했고,
그 반대(내가 지우면 사용자 것도 지워진다)도 성립했다.

**규칙**
- 작업 디렉터리 **밖**에는 쓰기·삭제 명령을 실행하지 않는다. 사용자가 실행할 명령을 안내한다.
- 재현 실험이 필요하면 환경변수로 경로를 작업 폴더 하위에 격리한다
  (예: `DOORAY_SYNC_STATE_DIR=<project>\.dbg\state`).
- 사용자 PC의 상태는 **사용자가 직접 실행한 명령의 출력**으로만 판단한다.

---

## 2. 재현되지 않는 문제는 추측하지 말고 진단을 코드에 심어라

**증상**: `설정 파일이 없습니다` — 파일은 실재하는데 프로그램이 없다고 함. 어시스턴트 환경에서는 재현 불가.

**오진 3회** (각각 근거를 들었으나 전부 틀림)

| # | 가설 | 반증 |
|---|---|---|
| 1 | 백신이 파일을 잠가 `os.path.exists`가 False 반환 | 결정적으로 재현됨 — 일시적 현상 아님 |
| 2 | Microsoft Store Python의 AppData 가상화 | Store Python 미설치 |
| 3 | 관리자 권한 상승으로 다른 계정 프로필 참조 | `관리자 권한: False`, 동일 계정 |

**해결**: 오류 메시지에 진단 정보(경로·존재 여부·실행 계정·폴더 내용·파이썬 경로)를 넣자
**한 번의 왕복으로** 원인이 잡혔다 — `APPDATA 총 항목 수: 17 vs 16`.

**규칙**
- 재현 안 되는 문제에 가설을 3개 이상 세우고 있다면, 그 시점에 **진단 출력을 만드는 쪽으로 전환**한다.
- 오류 메시지는 "무엇이 잘못됐다"가 아니라 **"내가 무엇을 어디서 보았는지"**를 담는다.
- 사용자에게 왕복 요청을 할 거면, 한 번에 판별 가능한 정보를 모아서 요청한다.

---

## 3. "완료" 보고 전에 사용자 측 증거를 확인하라

**사고**: "프로파일 4개 설정 완료"라고 보고했으나 **사용자 PC에는 아무것도 만들어지지 않았다**(§1 참조).
사용자는 그 말을 믿고 `push`를 시도했다가 실패했다.

**규칙**
- 어시스턴트 환경에서만 확인한 것은 "확인됨"이 아니다. **무엇을 어떻게 검증했는지 함께 밝힌다.**
- 사용자 환경에 대한 변경은 "내가 했다"가 아니라 "이 명령을 실행하시면 됩니다"로 전달한다.

---

## 4. 검증되지 않은 인과를 실측처럼 쓰지 말 것

**사고**: 검토보고서에 *"75페이지 스캔에서 429 백오프가 반복 발생해 6분이 걸렸다"*고 적었다.
**로그에 429 기록은 0건**이었다(클라이언트가 429를 자동 로깅하는데도). 실제 원인은 서버 응답 지연이었고,
산술로도 맞지 않았다(75요청 이론치 약 15초 vs 실제 359초).

독립 재감사로 **불일치 8건·근거부족 7건**이 나왔다. 그중 일부는 세션 중 실측했으나
**stdout으로만 출력하고 파일에 남기지 않아** 근거를 재현할 수 없었던 것들이다.

**규칙**
- 측정하지 않은 인과는 "추정"이라고 쓰거나 쓰지 않는다.
- 실측 결과는 **파일에 보존**한다(stdout은 사라진다). 이후 모든 프로브는 결과 JSON에 기록하도록 공정을 바꿨다.
- 자기 산출물은 **다른 관점으로 재감사**한다. 이 세션에서는 다른 모델이 원시 증거와 전수 대조해 잡아냈다.

## 5. 게이트는 "존재"가 아니라 "의미"를 검사하라

같은 실수를 두 번 했다.

**1차**: `SETUP.ps1`이 상태 DB **파일 존재**만 확인 → 빈 DB가 통과 →
그 상태로 push하면 원격에 이미 있는 파일을 신규로 오인해 **중복 업로드**(swstat 7건, spri2025 258건).
다행히 사용자가 `--dry-run`만 실행해 사고는 없었다.

**2차**: 이를 고쳐 **레코드 건수 > 0**으로 바꿨더니, 이번엔 정상적으로 비어 있는 신규 원격 폴더(spri2026)에서
오탐으로 막혔다. 검사하려던 진짜 명제는 "원격 스캔이 실제로 완료되었는가"이므로
`META_LAST_FULL_SCAN` 기록 여부를 봐야 한다.

**규칙**
- 게이트를 만들 때 **검사하려는 불변식을 문장으로 먼저 쓰고**, 그것을 직접 표현하는 값을 고른다.
- 프록시 지표(파일 존재, 건수)는 양방향 오류를 낸다 — 통과시켜선 안 될 것을 통과시키거나 그 반대.

> **2026-08-01 수정 완료.** `SETUP.ps1` 2-1 게이트를 `META_LAST_FULL_SCAN` 기준으로 교체했다.
> 양방향 검증함 — 스캔 완료·0건은 통과, 스캔 미완료 DB는 차단(`DOORAY_SYNC_STATE_DIR`로 격리 생성).
> 이 항목이 **문서에는 적혀 있었으나 코드는 고쳐지지 않은 채** 다음 세션으로 넘어갔다. §10 참조.

## 6. 병렬 구현 전에 인터페이스를 계약으로 고정하라

M1 구현은 서브에이전트 다수가 모듈을 나눠 동시에 작성했다. 성공 요인은
**`docs/모듈규약.md`를 먼저 확정**한 것이다 — 전 모듈의 시그니처·타입·예외·금지사항을 단일 진실 소스로 두고,
각 에이전트가 그것만 신뢰하게 했다.

결과: 18개 파일이 첫 통합에서 **임포트 오류 0건**으로 맞물렸다.

**규칙**
- 병렬 작성 전 계약 문서를 만든다. 계약이 없으면 통합 비용이 병렬 이득을 넘는다.
- 계약 문서에 **금지사항**(하지 말아야 할 것) 절을 둔다. 긍정 명세만으로는 위험한 구현을 막지 못한다.

## 7. 적대적 검증은 실제로 데이터 손실을 막는다

4관점(금지사항·계약준수·런타임·안전성) 리뷰 후 각 지적을 **반박하는** 검증 단계를 거쳐
**확정 결함 11건**(critical 3)을 얻었다. 전부 데이터 손실 계열이었다.

| 결함 | 방치했다면 |
|---|---|
| init 후 기준선이 비어 첫 push가 원격을 로컬로 덮어씀 | 원격 최신본 소실 |
| NFC 정규화 경로로 NFD 파일 접근 불가 | 해당 파일 영구 미백업(조용히) |
| 재-stat이 전송 **시작 전**에만 수행 | 다운로드 중 저장한 편집 소실 |

**규칙**
- "찾아라"만으로는 부족하다. 찾은 것을 **반박하게** 해야 오탐이 걸러지고 진짜만 남는다.
- 검증 관점에 **"이 코드가 데이터를 잃을 수 있는 경로"**를 반드시 넣는다.

---

## 8. 실계정 테스트가 잡는 것은 코드 리뷰가 못 잡는다

정적 검증을 모두 통과한 뒤 실제 계정에서 돌리자 두 가지가 나왔다.

- **네트워크 전송 계층 오류**(`RemoteProtocolError`)가 실제로 발생 — 재시도가 없어 init 전체가 실패했다.
  코드 리뷰로는 "일어날 수도 있다"까지만 알 수 있었다.
- **원격 순회 비용이 폴더 수에 비례**(폴더당 약 0.4초) — 드라이브 전체 지정 시 1시간 초과.
  실사용자는 업무 폴더 하나만 원한다는 사실이 실행 중에 드러나 `--remote-path` 옵션을 추가했다.

**규칙**: "완료"는 실제 대상에서 한 번 돌려본 뒤에 선언한다.

## 10. 교훈을 적었으면 같은 커밋에서 코드도 고쳐라

**사고**: 이 문서 §5에 게이트 오탐(spri2026)과 해법(`META_LAST_FULL_SCAN`)이 **이미 적혀 있었는데**
`SETUP.ps1`은 `count_files > 0`인 채로 커밋되어 있었다. 그래서 이번 세션이 같은 지점에서 다시 막혔고,
원인 진단을 처음부터 되풀이했다.

**왜 놓쳤나**: 교훈 문서에 쓰는 행위가 "처리했다"는 느낌을 준다. 문서는 지식을 남기지만
**동작을 바꾸지 않는다**. 게다가 `현재상태.md`는 여전히 반대 내용(§11)을 말하고 있어,
두 문서가 충돌한 채 방치됐다.

**규칙**
- 결함을 교훈 문서에 적을 때는 **코드 수정 여부를 같은 항목에 명시**한다 — "수정 완료" 또는 "미수정(사유)".
- 미수정으로 남긴다면 `현재상태.md`의 **미해결 작업 표에도 올린다**. 교훈 문서는 읽히지 않을 수 있다.
- 세션 시작 시 교훈 문서의 "미수정" 항목을 먼저 확인한다.

## 11. 인수인계 문서는 원인을 단정하지 말고 판별법을 써라

**증상**: `현재상태.md`에 *"SETUP.ps1이 멈추면 그 프로파일의 `init`이 실패한 것이다"*라고 적혀 있어,
실제로는 init이 성공했는데도 init 실패를 먼저 의심했다.

**원인**: 문서가 **증상**이 아니라 **원인**을 단정했다. 읽는 쪽에서는 검증 없이 통과시키는 전제가 된다.
§5의 진짜 원인이 이미 밝혀진 뒤에도 이 문장은 갱신되지 않았다.

**규칙**
- "멈추면 X가 실패한 것이다"가 아니라 **"멈추면 `python diag.py <프로파일>`로 스캔 시각과 기록 건수를 확인하라"**로 쓴다.
- 이미 적힌 원인 단정은 근거를 재확인하기 전까지 **가설로만** 취급한다.

## 12. "대상 0건"과 "일치 0건"은 다르다

**오진**: `reconcile -p workenv`의 `대조 대상 0건`을 보고
"로컬·원격에 겹치는 파일이 하나도 없다"고 사용자에게 잘못 보고했다.

**실제**: "대조 대상"은 *기준선이 없는* 교집합만 센다. workenv는 26건이 겹치되
**이미 기준선이 잡혀 있어서** 대상이 아니었다. 0의 의미가 "해당 없음"인데 "일치 없음"으로 읽었다.

**규칙**: 0을 근거로 결론을 말하기 전에 그 0이 **무엇을 세는 값인지** 확인한다.
여기서는 `diag.py`의 `키 교집합`이 실제 겹침 수이고 `reconcile 대상`은 그중 미해결분이다 — 둘을 같이 봐야 한다.

---

## 13. 잘린 출력은 산술로 교차검증한다

**증상**: `push --dry-run` 출력이 `... 외 297건`으로 잘려 총계를 알 수 없었다.
그대로 두면 계획에 누락·중복이 있어도 모른 채 3.18GB를 올리게 된다.

**규칙**: 화면에 보이는 것이 전부가 아니다. 독립적으로 계산해 대조한다.
spri2025는 `로컬 797건 − synced 258건 − 기존 원격폴더 42건 = 497건`이 계획 건수와 정확히 일치해
누락·중복 없음을 확인한 뒤 실행했다. 업로드 용량과 최대 파일 크기도 별도로 합산해 둔다.

---

## 14. 문서의 수치는 실행 직전에 전수 재측정한다

**증상**: `현재상태.md`는 플랜 한도(500MB) 초과 파일을 **1건**(spri2026의 589.5MB 동영상)으로 적고 있었다.
실제 스캔 결과 workenv에 **876.7MB**(`연구용sw/stata17/setupstata17.exe`)가 더 있었다 — 문서에 적힌 것보다 크다.

**원인**: 리스크 목록은 작성 시점의 표본이다. 이후 로컬 폴더가 바뀌면 갱신되지 않는다.

**규칙**: 한도·용량처럼 **실패를 유발하는 값**은 실행 직전에 전수 스캔으로 다시 센다.
문서는 "무엇을 봐야 하는지"의 단서로 쓰고, **수치의 근거로는 쓰지 않는다**.

## 15. 되돌리기 어려운 작업: 수치 제시 → 건별 승인 → 사후 검증

M1에는 삭제 경로가 없다. 잘못 올리면 수작업으로 지워야 한다(spri2025는 442개).

**실행 전** — 다음을 제시하고 승인받는다.

| 제시할 값 | spri2025 실제 |
|---|---|
| 신규 / 덮어쓰기 / 삭제 | 442건 / **0건** / **0건** |
| 용량 | 3.18 GB |
| 최대 파일 크기 (플랜 한도 대비) | 362.1MB (한도 이내) |
| 문서상 미확인 선결 항목 | 드라이브 여유 용량 미확인 |

승인은 **그 작업 하나에만** 유효하다 — spri2025 승인으로 나머지 프로파일까지 올리지 않는다.

**실행 후** — "실패 0건" 출력으로 끝내지 않는다.

| 확인 | 기대값 |
|---|---|
| `python diag.py <프로파일>` | `local_md5 보유` = `로컬 항목(파일만)`, `reconcile 대상 0` |
| `push --dry-run` 재실행 | `변경 없음` |

spri2025는 base 300 → 797(계획 497건과 정확히 일치), 로컬 700파일 전부 md5 보유,
재-dry-run `변경 없음`으로 확인했다.

## 16. 검증하려고 파괴적 재실행을 하지 않는다

## 17. 한글 `.ps1` 편집 후에는 인코딩·구문을 확인한다

`SETUP.ps1`은 UTF-8 **with BOM**이다. BOM이 사라지면 PowerShell이 CP949로 읽어 한글이 깨진다.
편집 후 세 가지를 확인한다.

1. BOM 유지 — 첫 3바이트가 `EF BB BF`
2. 구문 — `[System.Management.Automation.Language.Parser]::ParseFile()` 오류 0건
3. 한글 렌더링 — `Get-Content -Encoding UTF8`로 수정 구간을 다시 읽어 확인

깨졌다면 편집 도구 대신 `Set-Content -Encoding utf8`로 재작성한다.

## 18. "크기가 같으면 내용도 같다"는 실제로 틀렸다 ★

**상황.** 프로파일 통합 시 이미 올라간 1,334파일의 기준선을 어떻게 승계할지 3안이 있었다.
그중 B안이 `reconcile --trust-size` — 크기가 같으면 내용도 같다고 보고 원격을 받지 않는 것이었다.
7.2GB 다운로드를 통째로 아끼는 매력적인 선택지였다.

**적대적 검증이 기각했다.** 코드상 **불가역 로컬 소실 경로**가 성립한다.
잘못된 기준선이 `synced`로 박히면 → push가 `unchanged`로 건너뛰어 그 로컬 내용이 서버에
**한 번도 올라가지 않고** → 이후 원격에 새 버전이 생기면 pull의 로컬 보호가 (mtime, size)
일치로 풀려 → `os.replace`가 로컬을 덮는다. **서버에도 없고 로컬에서도 사라진다.**

**그리고 그 파일이 실재했다.** 같은 날 `writing` 프로파일의 정식 reconcile이 내용 불일치 4건을
찾았는데, 그중 **3건이 크기가 바이트 단위로 완전히 동일**했다.

| 파일 | 로컬 | 원격 | MD5 |
|---|---|---|---|
| `2018 상출제대기업.xls` | 16,384 | 16,384 | 불일치 |
| `data_181227_중대변화.xls` | 4,452,352 | 4,452,352 | 불일치 |
| `data_190507_기초통계.xls` | 29,696 | 29,696 | 불일치 |

`--trust-size`를 썼다면 이 3개를 잃었다. 가설로 기각한 시나리오가 몇 시간 뒤 실물로 나타났다.

**왜 흔한가.** `.xls`·`.hwp` 같은 레코드 기반 포맷은 셀·문단 내용이 바뀌어도 블록 길이가
보존되는 경우가 많다. 512바이트·4KB 배수로 딱 떨어지는 크기(16,384 / 29,696)가 그 신호다.

**규칙**
- 내용 동일성 판정에 **크기를 대리 지표로 쓰지 않는다.** 해시를 실제로 계산한다.
- "빠른 경로" 옵션이 정확성을 낮추는 방향이면, 아낀 시간과 **틀렸을 때의 손실**을 비교한다.
  여기서는 1시간 vs 파일 영구 소실이었다.
- 이 프로젝트의 제1원칙("동기화 안정성 > 편의기능")은 이런 갈림길에서 쓰라고 있는 것이다.

## 19. 실행 전에 반박시키면 계획이 바뀐다

WORK 통합은 81.75GB 불가역 업로드였다. 실행 전에 조사 4건 + 적대적 반박 3관점을 돌린 결과,
**1차 조사의 결론 여러 개가 뒤집혔다.**

| 1차 조사 | 반박 결과 |
|---|---|
| init 0건 상태로 push해도 "계획 단계 노출"일 뿐 | **틀림.** `upload_version`이 전 바이트 재전송 → 실제 81.5GB 송신 |
| 원격 근무환경에 로컬에 없는 것이 "약 104건" | **틀림.** **336건 / 0.99GiB** |
| reconcile 종료코드를 성공 신호로 쓸 수 있다 | **틀림.** '내용 다름'이 있어도 **종료코드 0** |
| A안은 6.71GB가 디스크에 쌓인다 | **틀림.** 한 개씩 받고 즉시 삭제 — 피크는 최대 파일 1개 |
| 인용 줄번호 | **32~39행씩 어긋남** — 검증 불가 |

마지막 항목이 특히 중요하다. **file:line을 인용하라고 요구해도 그 줄번호가 맞는지는 별개다.**
반박 단계가 실측(`grep -n`)으로 대조하지 않았다면 틀린 근거가 그대로 통과했을 것이다.

또 반박이 **실행 순서 오류**를 잡았다 — 구 프로파일을 work 생성 **이전에** 내려야 한다.
둘이 공존하는 동안 일괄 스크립트가 같은 파일을 두 프로파일로 각각 올릴 수 있고,
락이 프로파일별이라 막히지 않는다.

**규칙**
- 불가역 작업 전에는 계획을 **반박 전용 단계**에 넣는다. "검토해줘"가 아니라 "틀린 것을 찾아라".
- 근거로 제시된 줄번호는 **실측으로 대조**한다. 인용 형식을 갖췄다는 것이 정확하다는 뜻이 아니다.
- 반박에는 **서로 다른 관점**을 준다(데이터손실·중복·특정 이슈). 같은 질문 3번보다 훨씬 잡는다.

## 20. 되돌릴 수 있는 단계와 없는 단계를 갈라 실행한다

통합 절차 18단계 중 원격에 쓰는 것은 **16단계 하나뿐**이었다. 나머지는 전부 로컬이고 복구 가능하다.

**실제로 한 것** — 1~15단계를 먼저 끝내고 원격에 한 바이트도 쓰지 않은 상태에서 멈춘 뒤,
용량 확인과 승인을 받고 16단계로 갔다.

**규칙**
- 절차를 짤 때 **불가역 경계선을 먼저 긋고**, 그 앞의 모든 검증을 경계선 앞으로 몰아넣는다.
- 되돌리기 자산(백업)은 **경계선을 넘기 전에** 만들고 건수까지 검증한다.
  여기서는 상태 DB 4개를 sqlite backup API로 받고 기준선 700/621/13/104를 확인했다.
- **대안을 파괴하지 않는 순서를 고른다.** A안을 택하되 구 상태 DB를 남겨 C안을 fallback으로
  보존했다. 반대 순서(C안 먼저)는 A안을 되돌릴 수 없게 만든다.
- 도구가 위험한 지름길을 **화면에서 직접 권할 수 있다**(`--assume-local-newer`). 코드로 막을 수
  없다면, 그 안내문이 **뜨지 않는 상태**(보류 0건)를 게이트로 삼는 것이 유일한 실효 방어다.

## 21. 표를 코드로 옮기면 표에 없던 축이 생긴다

**상황**: 구현계획서 §3.3의 결정표는 13케이스를 `B/L/R` 세 축으로 정의한다. 그런데 코드로 옮기자
표에 **적혀 있지 않은 네 번째 축**이 나타났다 — "R을 이번에 실제로 관측했는가".

- 전체 순회 뷰: 목록에 없으면 **삭제**다.
- changes 델타 뷰: 목록에 없으면 **모른다**(변경이 없었을 뿐).

같은 "R 없음"이 정반대 의미다. 표는 이 구분을 담고 있지 않아서, 표만 보고 구현하면
둘 중 하나를 반드시 틀린다. 실제로 이 세션에서 **양방향으로 한 번씩** 틀렸다.

| 틀린 방향 | 결과 | 무엇이 잡았나 |
|---|---|---|
| 델타의 부재를 삭제로 읽음 | 폴더 개명 한 번에 하위 전체 오삭제(R8) | 설계 단계에서 인지 → `is_complete` 플래그로 분리 |
| 전체 뷰의 부재를 삭제로 안 읽음 | `--full` 재조정이 원격 삭제를 **영원히** 감지 못 함 | **테스트가 잡았다**(`test_full_view_absence_is_deletion`) |

두 번째는 코드를 다 쓰고 나서도 눈으로는 보이지 않았다. "완전 뷰에서는 부재가 삭제"라는
테스트를 **먼저 명제로 써 두었기 때문에** 실패로 드러났다.

**규칙**
- 명세가 표로 주어지면, 코드로 옮기기 전에 **표에 없는 축이 무엇인지** 먼저 적는다.
  (관측 여부, 부분 실패, 시각, 권한 — 표는 보통 '정상적으로 다 아는 상태'만 그린다.)
- 그 축의 양쪽 끝을 **각각 테스트 명제로** 고정한다. 한쪽만 막으면 반대쪽으로 틀린다.
- 안전한 기본값("모르면 아무것도 안 한다")은 한쪽 오류만 막는다. 반대쪽 오류는
  **조용한 미동작**이라 더 늦게 발견된다.

## 22. 파일럿이 도는 중에 하는 개발은 브랜치로 격리한다

파일럿 운용자는 `git pull` 후 `push`를 돌린다. 같은 브랜치에 M2 코드를 얹으면 그 다음 실행부터
**검증되지 않은 코드가 실계정을 만진다.** 이번에는 `m2-bidirectional` 브랜치로 분리하고
`현재상태.md` 맨 앞에 "파일럿은 `main`에서" 를 적었다.

기존 명령(`push`/`pull`)의 동작을 바꾸지 않는 것도 같은 이유다. 공유 코드를 고쳐야 하면
(이번의 대소문자 폴백처럼) **회귀 테스트를 먼저 붙이고** 고친다.

## 23. 테스트 전부 통과 = 무결함이 아니다 (실측 52 → critical 5)

**상황**: M2 구현을 끝내고 `tests` 52건이 **전부 통과**하는 상태에서 적대 검증 4관점을 돌렸다.
결과는 critical 5건 + major 8건이었다. 그중 하나는 M2 전체를 무력화하는 것이었다 —
업로드된 파일의 기준선(`local_md5`)이 NULL로 기록돼 **그 다음 실행부터 영원히 보류**되는 결함.
`sync`가 사실상 1회용이었는데, 52건 어디에도 걸리지 않았다.

**왜 안 걸렸나**: 내 테스트는 전부 **1패스**만 검증했다. "올라갔는가"는 봤지만
"**그 다음 실행이 정상인가**"는 보지 않았다. 동기화 도구의 결함은 대부분 2패스째에 나타난다.

**그리고 고치다가 두 번째 층이 나왔다.** 1차 수정(계산한 해시를 원본에 되쓰기)을 하고도
새로 쓴 회귀 테스트가 여전히 실패했다 — 신규 업로드 경로는 비교 대상이 없어 **해시를 계산할
이유 자체가 없기** 때문이었다. 불변식을 계산하는 쪽이 아니라 **기록하는 쪽(executor)**에
두어야 했다. 테스트를 먼저 실패시키지 않았다면 1차 수정에서 "고쳤다"고 끝냈을 것이다.

**규칙**
- 상태를 남기는 도구는 **연속 2회 실행**을 기본 테스트 형태로 삼는다.
  ("실행 → 결과 확인"이 아니라 "실행 → 재실행 → 아무 일도 없어야 함")
- 불변식은 그것을 **계산하는 곳이 아니라 기록하는 곳**에서 보장한다. 입력 경로는 여러 개고
  그중 하나는 반드시 계산을 건너뛴다.
- 수정 후 "테스트가 통과한다"가 아니라 **"이 테스트가 수정 전에는 실패했는가"**를 확인한다.
  이번에 대량삭제 게이트는 옛 코드에서 201건 삭제가 '1건'으로 통과하는 것을 실제로 재현해 확인했다.

## 24. 반박 단계가 죽어도 탐색 결과는 버리지 않는다 — 대신 내가 대조한다

검증 워크플로가 탐색 17건을 낸 뒤 **반박 단계 전체가 사용량 한도로 실패**했다.
반박 없는 지적은 오탐이 섞여 있으므로 그대로 코드에 반영하면 안 된다.

한 것: 각 지적을 **직접 코드로 대조**했다(`sed -n`으로 해당 줄을 읽고 실행 경로를 따라감).
17건 중 실제로 확인된 것만 고쳤고, 확인 과정에서 지적보다 **더 깊은 원인**을 찾은 것이 §23이다.

**규칙**
- 자동 검증이 중간에 죽으면 산출물을 폐기하지 말고 **검증 주체를 사람/자신으로 바꿔** 이어간다.
- 탐색과 반박은 비용이 다르다. 탐색이 살아 있으면 이미 대부분의 가치가 나와 있다.
- 인용된 줄번호는 반드시 직접 확인한다(§19). 이번에도 일부 지적의 줄번호가 어긋나 있었다.

## 25. 수정은 그 자체가 검증 대상이다 (13건 고쳤더니 4건이 새 결함)

1차 적대 검증에서 나온 13건을 고친 뒤, **수정분 자체를 검증 대상으로 다시 돌렸다.**
10건이 나왔고 **10건 전부 반박을 견뎠으며, 그중 4건이 내 수정이 만든 것**이었다.

가장 뼈아픈 것은 `resolve --keep local`이다.

| 시점 | 동작 | 사용자에게 보이는 것 |
|---|---|---|
| 원래 | 기준선을 NULL로 지움 → 영구 PROTECT | 매 실행 '보호' 목록에 뜸 (시끄럽지만 **보인다**) |
| 1차 수정 | 복원본 해시로 덮음 → 영구 무동작 | **'변경 없음'. 완전한 침묵** |

"고쳤다"가 아니라 **증상을 덜 보이게 만들었다.** 가시성이 나빠졌으니 오히려 후퇴다.
올바른 답은 기준선을 '마지막으로 동기화된 내용'(=원격본)으로 **유지**하는 것이었다 —
지우지도, 새 내용으로 덮지도 않는.

**규칙**
- 수정 후 검증은 "테스트가 통과하는가"가 아니라 **"수정분을 새 코드로 보고 다시 공격했는가"**다.
- 결함을 고칠 때 **증상이 사라지는 것과 원인이 사라지는 것**을 구분한다.
  증상만 죽이면 다음 발현은 더 조용하다.
- 안전장치를 고칠 때는 **가시성이 낮아지는 방향인지** 확인한다. 시끄러운 오동작이
  조용한 오동작보다 낫다.

## 26. 검토자의 수정안을 그대로 적용하지 않는다

이번 검증에서 "폴더판 결정표 7이 죽은 코드다. `MKDIR_LOCAL` 분기를 삭제하라"는 지적이 왔다.
분석은 정확했지만 **제안된 수정을 그대로 적용하면 더 큰 사고가 난다** — `init` 직후에는
원격 폴더가 로컬에 없는 것이 정상이라, 삭제 전파가 켜진 상태의 첫 `sync`가 원격 폴더를
전부 휴지통으로 보낸다.

반대로, 다른 지적에서는 검토자가 **내가 떠올리지 못한 부작용을 먼저 막아 주었다**:
"`_mark`에 file_id를 심어라"는 원안에 대해 "결정표 13에서는 옛 경로 레코드가 같은 id를
들고 있으니 중복 행이 생긴다"며 조건을 붙여 왔다.

**규칙**
- 검토 결과는 **문제 지적**과 **해결 제안**을 분리해 받는다. 전자의 정확도가 후자보다 훨씬 높다.
- 제안된 수정은 "이 코드가 처음 실행되는 상태(init 직후, 빈 DB, 첫 동기화)"에 넣어 보고 나서 적용한다.
- 반박 단계에 "제안된 수정이 새 결함을 만드는가"를 명시적으로 묻게 하면 실제로 걸러진다.

## 27. 페이크는 "내가 믿는 서버"다 — 틀린 믿음은 테스트에 그대로 복사된다

**사고**: M2 델타 모드가 실계정에서 원격 변경을 **하나도 못 봤다.** 원인은 커서에 실려 나가는
`fileId` 파라미터였다. 이걸 넣으면 넣지 않았을 때 반환되는 항목이 누락된다(A/B 대조로 확정).

**왜 자동 테스트 71건이 못 잡았나**: 페이크 클라이언트를 내가 만들었고, 나는 `fileId`가
페이징 보조키라고 **믿고 있었으므로** 페이크가 그것을 무시하도록 짰다. 그래서 테스트는
"내 믿음대로 동작하는 서버"에 대해서만 통과했다. 실제 서버는 다르게 동작했다.

더 나쁜 것은 그 믿음의 출처다 — **검토보고서에 실측으로 적혀 있었다.**

> "동일 revision에 항목 2건 공존 → `(revision, fileId)` 복합 커서가 필수인 이유"

관측(동일 revision 공존)은 옳았다. 거기서 끌어낸 **해법**이 틀렸고, 그 해법이 검증 없이
규약 → 코드 → 페이크 → 테스트로 네 번 복사됐다. M1은 changes를 소비하지 않아
(push/pull은 목록 API) 이 전제가 **한 번도 실행되지 않은 채** 통과 상태로 남아 있었다.

**규칙**
- 페이크로 검증한 것은 **"서버가 이렇게 동작한다면 내 코드는 옳다"**까지다. 서버가 정말
  그렇게 동작하는지는 별개의 실측이 필요하다.
- 실측 기록은 **관측**과 **거기서 끌어낸 해법**을 분리해서 적는다. 후자는 가설이며,
  실제로 실행해 보기 전까지는 검증되지 않은 것으로 취급한다.
- **한 번도 실행된 적 없는 코드 경로의 전제**를 목록으로 관리한다. M1에서 changes 소비가
  그랬다 — 규약에 적혀 있고 테스트도 있었지만 실행된 적은 없었다.
- 원인을 모를 때는 **변수 하나만 바꾼 대조 실험**을 만든다. 이번에는 같은
  `latestRevision`에 `fileId` 유무만 달리한 A/B가 한 번에 결론을 냈다(교훈 §2의 연장).

## 28. 동료 PC에 배포되는 파일은 "그 PC의 로케일"로 읽힌다 — requirements는 ASCII 전용

**사고**: 동료 PC(신규 설치)에서 `설치.bat` 3/6 단계가
`UnicodeDecodeError: 'cp949' codec can't decode byte 0xeb in position 14`로 중단됐다.
원인은 `requirements.txt` 1행의 한글 주석("런타임"의 첫 바이트가 정확히 position 14).
pip은 requirements 파일에 BOM이 없으면 **로케일 코덱(한국어 Windows = cp949)**으로
읽는다. 개발 PC에서는 의존성이 이미 깔려 있어 이 경로가 실행된 적이 없었고,
테스트도 pip의 파일 읽기를 거치지 않으므로 원리상 잡을 수 없었다.

같은 계열 사고가 다른 프로젝트(newsletter_system: 한글 경로 cp949 충돌,
INSTALL_FROM_GITHUB.md에 기록)에서도 있었지만, **pip-requirements 변형은 어느
기록에도 없어** 재발했다. 전역 CLAUDE.md의 cp949 패턴 목록에도 이 변형을 추가했다.

**규칙**
- **다른 PC의 다른 프로그램이 읽는 파일은 ASCII 전용**으로 유지한다 —
  requirements.txt, .bat(§17의 synchere 사례), 설정 키. 한글 설명은 docs/에 쓴다.
- 설치 스크립트의 pip 호출은 `PYTHONUTF8=1`로 감싼다(재유입 대비 이중 방어 —
  이 값이면 pip의 로케일 폴백이 UTF-8이 된다).
- "개발 PC에서 잘 되는 설치"는 검증이 아니다 — 설치 경로는 **의존성·설정·상태가
  없는 환경**에서만 실행되는 분기를 가지며, 그 분기는 새 PC에서 처음 실행된다.
