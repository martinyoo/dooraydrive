이 문서의 모든 시각·소요시간은 다음 세 가지 근거로만 산출했으며, 추정치는 명시적으로 표시했다.

| 출처 | 신뢰도 | 비고 |
|---|---|---|
| 세션 트랜스크립트 (사용자 메시지·도구 호출·도구 결과의 UTC 타임스탬프) | **최고** | 사용자 응답 대기시간은 질문(AskUserQuestion/ExitPlanMode) 발신 시각과 사용자 응답(tool_result) 수신 시각의 차이로 정밀 산출. KST = UTC+9 환산 |

| 백그라운드 에이전트·Workflow 완료 통지의 자체 보고 소요시간(`duration_ms`) | 높음 | 트랜스크립트 실측 시각과 교차검증 — 두 사례 모두 오차 1초 이내로 일치 |
| 파일시스템 타임스탬프 | 보조적 | PoC 스크립트 파일들의 생성시각 순서가 실제 작성 순서와 어긋나는 현상이 발견되어(백신·동기화 에이전트의 비동기 메타데이터 갱신 추정) 세부 순서 근거로는 사용하지 않음. 다회 수정 파일의 최종 저장 시각(LastWriteTime) 확인용으로만 사용 |

같은 세션에서 "실측처럼 보이지만 근거가 없는 서술"을 감사로 발견한 사례가 있어(§5 참조), 이 문서에도 동일한 기준을 적용했다.

## 5. 특기사항 — 품질 관리 사례

발표자료에 인용할 만한, 이 세션에서 실제로 발생한 자기수정 사례 두 가지.

**① PoC 실행 중 버그 자기수정**
PoC-05 1차 실행이 전 시나리오에서 실패했다. 최초 가설("드라이브에 쌓인 대량 과거 삭제 이력에 신규 변경사항이 파묻혔다")을 세우고 조사했으나, 후속 재검증에서 이 가설 자체가 틀렸음이 밝혀졌다 — 진짜 원인은 changes API가 요청 크기보다 적은 개수를 반환하면서도 뒤에 데이터를 남겨두는 특성 때문에 커서가 과거 시점에 고착된 것이었다. 원인을 정확히 규명해 스크립트를 수정한 뒤 재실행하여 8개 시나리오 전부를 정상 확인했다.

**② 검토보고서 자기검증**
사용자가 "보고서를 어느 모델이 작성했는지" 질문한 것을 계기로, Fable 5가 자신이 아닌 다른 모델(Sonnet 5)이 작성한 보고서 구간을 원시 증거(JSON/로그)와 전수 대조하는 재감사를 수행했다. 그 결과 핵심 발견 3가지(부분 페이지 반환, 폴더 하위 이벤트 미발생, 이름변경 시 버전 불변)는 원시 증거와 정확히 일치했으나, 보조 서술에서 불일치 8건·근거부족 7건을 확인했다(예: "rate limit으로 인한 429 반복 발생"이라는 서술이 실제 로그에는 근거가 없었음, changes API의 성격을 "이벤트 로그"로 오해했던 부분을 "파일별 최종상태 뷰"로 재해석). 수정은 별도로 진행 중이다.

**교차검증 정확도**: 백그라운드 에이전트·Workflow의 자체 보고 소요시간과 세션 트랜스크립트 실측 시각을 대조한 결과 두 사례 모두 오차 1초 이내로 일치했다.
