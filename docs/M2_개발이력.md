## 2. 개발 과정 — 무엇이 언제 드러났나

이 절이 이 문서의 핵심이다. **"어떻게 만들었나"보다 "무엇을 놓쳤고 그게 언제 잡혔나"**가
다음 세션에 쓸모 있다.

### 1단계. 계약 먼저, 그다음 구현 (08-02)

M1의 교훈(§6)대로 `모듈규약_M2.md`를 먼저 고정하고 구현했다. 초기 자체 검토에서 5건 수정.

### 2단계. 적대적 검증 1차 — 테스트 52건 통과 상태에서 critical 5건

4관점 탐색(데이터손실 / 불변식 / 런타임 / 실규모) → **13건 확정**. 대표적인 것:

- **업로드된 파일의 기준선이 NULL로 기록** → 그 파일은 다음 실행부터 영원히 보류.
  `sync`가 사실상 1회용이었다. 요약에는 "올림 N건"이 찍혀 사용자는 백업된 줄 안다.
- **대량삭제 게이트 무력화** — 서브트리를 접은 *뒤*의 동작 수를 세어, 폴더 통삭제가
  "삭제 1건"으로 통과. 옛 코드에서 201건 삭제가 통과하는 것을 재현해 확인했다.
- **`local_trash`에 삭제 직전 재-stat 없음** — 삭제는 계획 맨 마지막에 실행되므로,
  앞선 전송 수 분 동안 저장한 편집이 그대로 휴지통행.

> 이때 배운 것: **테스트 전부 통과 = 무결함이 아니다.** 내 테스트는 전부 1패스만 검증했고,
> 동기화 도구의 결함은 대부분 **2패스째**에 나타난다(교훈 §23).

### 3단계. 적대적 검증 2차 — **수정분 자체를 검증** → 10건, 그중 4건이 내가 만든 것

1차 수정 13건을 적용한 뒤 수정분을 새 코드로 보고 다시 공격했다. 10건 제기 → **10건 전부
반박을 견뎠고**, 4건이 1차 수정이 만든 결함이었다.

가장 뼈아픈 것은 `resolve --keep local`이다.

| 시점 | 동작 | 사용자에게 보이는 것 |
|---|---|---|
| 원래 | 기준선을 NULL로 지움 → 영구 PROTECT | 매 실행 '보호'에 뜸 — 시끄럽지만 **보인다** |
| 1차 수정 | 복원본 해시로 덮음 → 영구 무동작 | **'변경 없음'. 완전한 침묵** |
| 최종 | 기준선을 원격본 해시로 **유지** | 다음 sync가 `새버전업로드`로 실제 업로드 |

고친 게 아니라 **증상을 안 보이게** 만들었다. 가시성이 나빠졌으니 후퇴다(교훈 §25).

### 4단계. 실계정 검증 — 자동 테스트가 **원리상** 못 잡던 결함 5건

시험 프로파일 두 개(`m2test`/`m2peer`)를 '두 대의 PC'처럼 써서 검증했다.

- **커서에 `fileId`를 실으면 원격 변경을 영구히 놓친다.**
  검토보고서 초판이 "동일 revision 공존 → `(revision, fileId)` 복합 커서 필수"라고
  **결론**했고, 그 결론이 규약 → 코드 → 페이크 → 테스트로 네 번 복사됐다.
  관측은 옳았고 **해법이 틀렸다.** M1은 changes를 소비하지 않아 한 번도 실행된 적 없었다.
  → [검토보고서 §3.2](검토보고서.md)에 A/B 대조표와 함께 정정 기록.
- **`init` 직후 안 받은 파일을 '로컬 삭제'로 판정.** 삭제 전파가 켜져 있으면
  **새 PC의 첫 `sync`가 원격 파일을 전부 휴지통으로 보낸다.** 폴더에는 같은 구분을
  넣어 두고 파일 경로에는 적용하지 않아 생긴 결함이다.
- **중단된 전송의 `.part`가 영구히 남는다.** `download`가 임시파일 경로를 저널에
  기록하지 않아 복구가 지울 대상을 몰랐다.
- **대량삭제 비율 임계가 작은 폴더에서 정상 삭제까지 막는다.** 파일 5개에서 20%는 1건.
  사용자가 습관적으로 `--allow-bulk-delete`를 붙이게 되어 안전장치가 무력화된다.
- **`resolve --keep local/remote`가 원격 충돌 사본을 남겨** 다음 sync가 다시 받아온다.

각 결함의 상세와 조치는 [구현계획서.md](구현계획서.md) §5 M2의 표에 있다.

## 4. 다음 세션이 알아야 할 것

### 설계상 꼭 기억할 것

1. **원격 뷰는 자기 완전성을 안다.** 델타에서 "안 보임"은 삭제가 아니라 미관측이다(I1).
   반대로 **전체 뷰에서 부재는 삭제다.** 이 둘을 섞으면 한쪽으로 반드시 틀린다.
2. **복구는 상태를 복원하지 않는다.** sync_status만 재검사 대상으로 바꾸고, base 값은
   손대지 않는다. 추정으로 채우면 반쪽 기준선이 조용한 손실을 만든다(I4).
3. **기준선 없는 `synced`를 만들지 않는다.** 그 조합은 파일을 영원히 보류로 만든다.
   불변식은 계산하는 쪽이 아니라 **기록하는 쪽(executor)**에서 보장한다.
4. **커서에 `fileId`를 넣지 않는다.** (§2 4단계 참조)

### 검증할 때

- **연속 2회 실행**을 기본 테스트 형태로 삼는다. "실행 → 재실행 → 아무 일도 없어야 함".
- 페이크는 "내가 믿는 서버"다. 페이크로 통과한 것은 **서버가 그렇게 동작한다면** 옳다는
  뜻일 뿐이다(교훈 §27).
- CLI 출력으로 판정할 때 **라벨 존재로 검사하지 말 것.** `_kv` 표는 값과 무관하게 라벨을
  항상 출력하므로 `"변경 없음" in out` 같은 검사는 **실패할 수 없다**(교훈 §5의 재발).

### 실업무 첫 적용 (2026-08-04) — M2 운용 검증 완료

가장 작은 파일럿 프로파일 `swstat`(14항목)에 `sync`를 처음 적용했다.

| 단계 | 결과 |
|---|---|
| `--dry-run` | `실제로 사라질 항목: 0건`, 계획 `변경 없음` |
| 1패스 실행 | `변경 없음`. 커서 **17856 → 23828**(밀려 있던 changes **5,950건** 소비), 관측 7건 |
| 2패스 | `changes 0건` — 수렴 |
| 사후 | 14항목 전부 `synced`, 미해결 충돌 0, 미완료 저널 0, reconcile 대상 0 |
| M1 무영향 | `push --dry-run` = `변경 없음` |

> **커서에 `file_id`가 실려 보이는 것은 정상이다.** `Cursor.as_params()`는
> `latestRevision`만 보내고 `file_id`는 진단용으로만 보관한다(models.py). 마지막으로
> 소비한 항목이 기록될 뿐이며, 변경이 0건인 패스 뒤에는 비어 보인다. 이것을 결함으로
> 오인해 커서를 건드리면 §2 4단계의 결함을 되살리게 된다.

첫 실행은 init 이후 쌓인 드라이브 전체 변경을 훑느라 시간이 걸린다(대부분 다른 폴더 건이라
경로 필터에서 걸러진다). 오래 걸리면 `--full`이 더 빠를 수 있다.

정리 명령:

```bash
python tools\m2_scenario.py --cleanup-only    # 원격 _m2_test 를 휴지통으로(복구 가능)
```
