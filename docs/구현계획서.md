### 3.2 상태 DB 스키마 (요지)

```sql
PRAGMA journal_mode = WAL;

CREATE TABLE files (              -- 3-way diff의 base = "마지막 동기화 시점"
  file_id         TEXT,           -- 원격 id. deleted 톰스톤 역참조용 (필수)
  drive_id        TEXT NOT NULL,
  rel_path        TEXT NOT NULL,  -- NFC, '/' 구분자
  rel_path_key    TEXT NOT NULL,  -- casefold: Windows 대소문자 충돌 검출
  is_dir          INTEGER NOT NULL,
  local_mtime_ns  INTEGER, local_size INTEGER, local_md5 TEXT,
  remote_revision INTEGER, remote_version INTEGER, remote_md5 TEXT,
  server_name     TEXT,           -- 서버 저장명 정본 (공백 절삭 대응, R14)
  sync_status     TEXT NOT NULL DEFAULT 'synced',
     -- synced|pending_upload|pending_download|conflict|unsyncable|error|ignored
  UNIQUE (drive_id, rel_path_key)
);
CREATE TABLE journal   (...);     -- 크래시 복구 근거 (세션uuid, op, phase, detail JSON)
CREATE TABLE conflicts (...);     -- 충돌 사본 경로·종류·해결 여부
CREATE TABLE meta      (...);     -- revision_cursor, cursor_file_id, last_full_scan_at, hash_algo
```

### 3.3 3-way diff 결정표 (B=base, L=로컬, R=원격)

| # | 상황 | 판정 | 동작 |
|---|---|---|---|
| 1 | B없음 · L있음 | 로컬 신규 | 이름 존재 확인 → POST (409 시 재조회 후 재판정) |
| 2 | B없음 · R있음 | 원격 신규 | 원자적 다운로드 |
| 3 | B없음 · 양쪽 신규 | 경로 충돌 | MD5 동일→병합(기록만), 다르면 로컬 충돌사본 + 원격 다운로드 |
| 4 | L변경 · R불변 | 로컬 수정 | PUT 새 버전 |
| 5 | L불변 · R변경 | 원격 수정 | 다운로드 (교체 직전 재-stat, 어긋나면 6번) |
| 6 | L변경 · R변경 | **충돌** | 로컬 → `이름 (충돌 YYYY-MM-DD HHMM).ext` 보존 → 원격 다운로드 → 사본 업로드(기본 on) |
| 7 | L삭제 · R불변 | 로컬 삭제 | 원격 휴지통 이동 (`propagate_deletes` 기본 — 2026-08-11부터 `true`. 꺼져 있으면 보고만) |
| 8 | L불변 · R삭제 | 원격 삭제 | 로컬 Windows 휴지통 (동일 기본값) |
| 9 | L삭제 · R변경 | 삭제 vs 수정 | **보존 승리** — 전파 안 함, 재다운로드, 보고 |
| 10 | L변경 · R삭제 | 수정 vs 삭제 | **보존 승리** — 신규 재업로드, 보고 |
| 11 | L이동/개명 | 로컬 이동 | 원격 move/rename API |
| 12 | R이동/개명 | 원격 이동 | 로컬 `os.replace` |
| 13 | 이동+수정 복합 | 복합 | 이동 먼저 반영 후 4/5/6 재적용, 판단 불가 시 6번 |

- 원격 변경 감지 키: **`(version, name, path)`** (이름 변경은 version 불변 — R13)
- 내용 동일성 보조 판정: **MD5** (가짜 충돌 제거)
- 이동 승격: "삭제+동일 (size,MD5) 신규" 쌍 → 이동으로 재해석 (deleted가 이기지 않는 안전망과 이중)

## 4. 실측이 강제한 구현 규칙 (코드 반영 체크리스트)

구현 시 각 항목을 담당 모듈·단위 테스트와 함께 고정한다. 근거는 검토보고서 §3.

**A. api/client.py (단일 관문)**
- A1. 모든 응답에서 `header.isSuccessful`/`resultCode` 검사 — **HTTP 200이어도 실패일 수 있음**(실측 resultCode=-15700100). 실패 시 fail-stop 정책 연동
- A2. raw 전송의 307 수동 처리 — Location 재요청에 Authorization 재부착(무인증 401 실측). 업로드는 multipart 재구성(파일 재오픈)
- A3. rate-limit 헤더 기반 선제 감속: `Remaining < 5` 시 `1/Replenish-Rate` 간격 삽입. 429 시 Retry-After 우선 백오프. **file 객체 업로드는 자동 재시도 금지**(소진 문제)
- A4. 타임아웃: connect 10s / read 600s / write 1800s. changes 쿼리는 응답이 느림(~5초/요청)을 전제로 폴링 예산 설계

**B. core/remote.py (changes 소비)**
- B1. 델타 수집 종료 조건은 **0건 응답뿐** (`len < size` 금지 — 단위 테스트로 회귀 방지, R11)
- B2. 커서는 **revision 단조** — '완전히 소비한 마지막 revision'까지만 전진하고, 같은
  revision 한가운데서 끊기면 직전 완전 소비 지점으로 물러난다([remote.py:293](../dooray_sync/core/remote.py)).
  ~~`(revision, fileId)` 복합~~은 2026-08-03 철회 — changes 질의에 fileId를 싣지 못해
  성립하지 않는다(`api/drive.py` 주석 "revision만 비교한다"). **재도입 금지.**
- B3. **net-뷰 전제**: 항목의 name/path를 정본 수용, 미지 id의 deleted는 무시(정상), deleted는 id·type·revision만 옴 → DB 역참조
- B4. 폴더 `updated` 수신 → **해당 폴더 하위 트리 목록 재열람** (R8 — 대량 오삭제 방지의 핵심)
- B5. 초기 스캔·전체 재조정은 목록 API(엄격 페이지네이션 실측 확정)로, changes 전량 스캔은 초기 커서 확보 시 1회만

**C. core/executor.py + util/paths.py (로컬 안전)**
- C1. 원자적 다운로드: 동기화 루트 내 `.dooraysync\tmp\` → size+MD5 검증 → `os.replace`
- C2. 교체 직전 재-stat — 스캔 시점과 다르면 중단 → 충돌 전환
- C3. 모든 로컬 IO에 `\\?\` 접두 상시 적용 (끝 점 절삭·260자 실측 근거)
- C4. **업로드 응답의 서버 저장명을 정본으로 DB 기록** (서버가 앞뒤 공백 절삭 — R14 재전송 루프 방지). 로컬명≠서버명이면 사용자 통지 후 로컬명 정규화
- C5. 삭제는 휴지통만(원격 move-to-trash / 로컬 send2trash). `propagate_deletes` 기본값은 2026-08-11부터 `true`, 대량삭제(50개 또는 20%) 자동 중단. **폴더 휴지통 이동은 하위 재귀 적용됨을 전제**로 중복 move 시도하지 않음(이미 휴지통인 항목의 move는 실패 정상 처리)
- C6. exclude 기본값: `~$*, *.tmp, *.part, Thumbs.db, desktop.ini, .dooraysync/, *.crdownload`

**D. 업로드 분기 (core/planner.py)**
- D1. 대상 폴더에 동일 이름 존재 → `PUT ?media=raw`(새 버전) / 부재 → `POST`. 409 수신 = 경쟁 상태 신호 → 재조회 후 재판정 (409는 순수 이름 충돌, 실측 확정)

## 5. 마일스톤별 구현 계획

### M1. 수동 단방향 push/pull — **구현 완료 (2026-07-31)**

실계정 스모크 테스트 통과: `init`(범위 지정) → `push`(폴더 2 + 파일 3) → `push` 재실행(재전송 0건)
→ 로컬 수정 후 `pull`(수정본 보호) → 로컬 삭제 후 `pull`(내용·크기 정확히 복원). 회귀 테스트 19건 통과.

**구현 중 발견해 수정한 결함** (적대적 검증 4관점 + 실계정 테스트)

| 심각도 | 결함 | 조치 |
|---|---|---|
| critical | `init` 후 로컬 기준선이 비어 첫 `push`가 원격을 로컬로 덮어씀 | 기존 기준선 승계 + 기준선 없는 파일은 **업로드 보류**(`--assume-local-newer`로만 강행) |
| critical | NFC 정규화한 경로를 물리 경로로 재사용 → NFD 이름 파일 접근 불가 | `LocalEntry.disk_path`에 디스크 원본 표기 보존, FS 접근은 전부 이 값 사용 |
| critical | C2 재-stat이 전송 **시작 전**에만 수행 → 다운로드 중 저장한 편집 소실 | `download(pre_replace_guard=...)`로 **os.replace 직전** 재검증, 불일치 시 보호 처리 |
| major | `os.replace` 전 `fsync` 없음 → 정전 시 원본·신본 동시 손상 | 임시파일 close 전 `flush`+`fsync` |
| major | 폴더 생성 시 로컬명을 정본으로 기록(R14 위반) | `create_folder_full`이 서버 저장명 확정 후 반환 |
| major | 서버 개명 시 `pull`이 중복 로컬 파일 생성 | `file_id` 역색인으로 중복 감지 → 보호 |
| major | 해시 실패 파일이 조용히 제외되어 종료코드 0 | `hash_failures`로 구조화, DB error 기록 + 종료코드 반영 |
| major | `init`이 원격 순회 내내 쓰기 락 보유 | 순회(네트워크)와 DB 쓰기 분리 |
| **major** | **전송 계층 오류를 재시도하지 않아 순회 중 1회 끊김에 전체 실패** | `httpx.TransportError` 재시도 추가 (실계정에서 실제 발생) |

**실계정 테스트로 드러난 설계 보완**: 원격 전체 순회는 폴더 수에 비례(폴더당 약 0.4초)해 대형 드라이브에서 1시간을 넘긴다. 실사용자는 드라이브 전체가 아니라 업무 폴더 하나를 원하므로 **`--remote-path`로 동기화 범위를 하위 폴더로 한정**하는 옵션을 추가했다.

### M2.5 운용 계층 확정 — 폴더별 synchere ↔ 전체 config 역할분담 (2026-08-07)

M3(자동 데몬) 착수 전에 두 층의 역할을 확정한다. 기존 판정(2026-08-07 3자 적대
검토: config가 실행의 정본, 마커는 정의가 아니다)은 유지하되, 사용자 요구에 따라
**로컬 마커를 '등록/해제 스위치'로 승격**한다 — 마커는 실행 시점의 판단 근거가
아니라, **관찰될 때 config를 고쳐 쓰는 입력**이다. 실행은 여전히 config만 본다.

| 층 | 소유 | 역할 |
|---|---|---|
| `config.toml` (`sync_mode`/`sync_note`) | 프로그램, PC별 | **실행 정본.** CLI `sync` 게이트·SYNC.ps1 필터·synchere 실행 여부 전부 이것만 본다 |
| 로컬 `synchere.bat` — 프로파일 루트 | 사용자 | ① 실행기(더블클릭) ② **등록/해제 스위치** — 복사해 실행하면 등록, 지우면 해제 |
| 로컬 `synchere.bat` — 그 외 위치 사본 | 사용자 | 실행기만(하위 사본 = 품는 프로파일 실행, WORK 사본 = 하위 일괄 실행). 등록 상태와 무관 |
| 원격 `synchere.bat` — 원격 루트 | config에서 단방향 파생 | 발견 힌트(2번째 PC `-Discover`). 엔진 비가시(양축 ALWAYS_EXCLUDE) 유지 |

**전이 규칙** — 구현은 `tools/sync_here.py`의 `reconcile_markers` **한 곳**이다
(synchere 실행 경로가 직접 호출, `SYNC.ps1 -Sync`는 `--check-markers`로 호출.
이중 정책 표를 폐지한 전례를 반복하지 않는다).

| # | 관찰 | 동작 |
|---|---|---|
| 1 | 미등록 폴더에서 마커 실행 | 형제 유도 자동 등록(`64fa3ef`) 후 sync. 등록 직후 루트에 로컬 마커를 놓아 '등록 = 마커 ON' 불변식 유지. 형제 없으면 안내만(원격 경로 추정 불가) |
| 2 | `sync_mode='sync'`인데 루트에 마커 없음 | **자동 해제**: `off` + `[synchere-off]` 태그 노트 기록, 이번 실행 제외·보고 |
| 3 | `off` + `[synchere-off]` 태그인데 마커 있음(재복사 후 실행/스윕) | **자동 재등록**: `sync` 복귀 후 실행 |
| 4 | `push`/`pull`/태그 없는 `off` (workenv·study·writing 등 사람의 결정) | **자동 전환 절대 금지** — 사유·수동 명령 안내만. 더블클릭 한 번이 1GB 수신 결정(workenv)이나 안전 보류(writing)를 뒤집으면 안 된다 |

설계 근거:

- **해제는 soft-delete다** — 프로파일 항목·기준선 DB를 남기고 `sync_mode=off`로만
  기록한다. 일시적 마커 부재(Google Drive 재동기화·백신 격리·오프라인 드라이브)가
  등록 정보를 파괴하지 못하게 하고, 재등록을 더블클릭 한 번으로 만든다. 항목 자체를
  지우면 기준선이 고아가 되고 재등록 시 재-init이 필요해진다. 완전 제거를 원하면
  config에서 수동 삭제.
- **해제는 원격 마커를 지우지 않는다** — 삭제 무전파 원칙 + 다른 PC의 발견 힌트.
  원격 정리는 `tools/trash_toolfile.py` 수동.
- **적용 지점은 운용 진입점이다**: synchere 실행(상향·하향)과 `SYNC.ps1 -Sync`.
  **CLI `dsync sync`는 마커를 계속 모른다** — 격리 시험 프로파일(M2 실계정 검증·
  사용자 테스트 절차)이 마커 없이 돌아야 하고, 엔진 비가시 원칙을 유지한다.
  이 경계는 의도된 것이다: 전문가용 CLI 직접 호출은 config 정본을 따른다.
- **dry-run은 config를 쓰지 않는다** — 해제는 미리보기 일관성을 위해 그 실행의
  메모리에서만 제외하고, 재등록은 예고만 한다(기록 없이 돌리면 CLI 게이트가 거부).
  `SYNC.ps1 -DryRun`은 별도 프로세스라 이 메모리 상태가 전달되지 않으므로,
  `--emit-modes <파일>`로 유효 mode를 받아 미리보기 대상 집합을 실제 실행과
  일치시킨다(재등록 예정은 예고만 하고 계획 산출은 실제 실행 시).
- **WORK 스윕은 등록하지 않는다** — 하향 실행은 이미 등록된 대상만 돈다. 미등록
  폴더의 등록은 그 폴더의 마커를 **직접 실행**할 때만(스윕 한 번이 7.6GB 초기
  업로드를 암묵 개시하면 안 된다).
- **'등록 = 루트에 마커 ON'은 모든 등록 경로의 불변식이다** — 형제 유도 등록·
  `set_sync_mode X sync`·`SETUP-2ND-PC.ps1`이 각각 등록 직후 마커를 배치한다.
  마커 없이 sync로 등록되면 다음 정합이 도로 해제하기 때문. `dsync init` 직접
  호출만은 예외(엔진은 마커 무지) — 이후 첫 synchere/스윕 실행에서 해제 안내가
  나오고, 마커 복사 한 번으로 복귀한다.
- **판단 불가는 해제 근거가 아니다** — 마커 존재는 3상(있음/없음/판단 불가)으로
  판정하고, 권한·잠금으로 확인 불가면 config를 바꾸지 않는다(`os.path.exists`는
  오류를 False로 뭉갠다 — config 읽기에서 실측으로 배운 함정과 동일).
- **사람이 모드를 명시하면 자동 태그를 걷는다** — `set_sync_mode`로 모드를 정하면
  `[synchere-off]` 태그가 제거돼, 이후 마커 파일이 (GDrive 복원 등으로) 되살아나도
  자동 재등록되지 않는다. 자동 상태와 수동 상태의 경계는 태그 하나다.
- **note는 cp949 안전 문자만** — sync_note는 SYNC.ps1이 cp949 파이프로 되읽으므로
  자동 생성 note에 em dash(—) 등 비인코딩 문자를 넣지 않고, 읽는 쪽도
  `errors='replace'`로 크래시를 막는다.

**적대 검증 (2026-08-07, 3패스)** — 1차 5관점 26건 제기 → 12건이 반박을 견뎠고
전부 수정했다. 주요 확정 결함: `SYNC.ps1 -DryRun` 미리보기가 실제 실행과 반대
집합을 보여줌(프로세스 경계에서 메모리 정합 소실), 안내되는 전환 명령
