# M1~M2 사용자 테스트 (시나리오 + 실행 결과)

- 실행: 2026-08-04 · 브랜치 `m2-bidirectional` · 실계정(공공 클라우드)
- 목적: M3(자동 데몬) 착수 전, **사용자 관점**으로 M1(push/pull)과 M2(sync/충돌/복구)를
  실계정에서 검증한다. 시나리오는 기존 동기화 도구(Google Drive·Dropbox·OneDrive·Syncthing)의
  **실제 충돌 사고 사례**에서 도출했다.
- 결과 요약: **시나리오 20종 실행, 결함 3건 발견·수정**(전부 회귀 테스트 추가),
  자동 테스트 84 → **88건 통과**. 유실 0건 · 예상 밖 삭제 0건.

## 0. 격리 (파일럿 데이터 보호)

모든 테스트는 파일럿 프로파일(`spri2025` 등)과 완전히 분리된 환경에서 실행했다.

| 항목 | 값 |
|---|---|
| 설정/상태 | `DOORAY_SYNC_CONFIG_DIR=.dbg\ut\cfg` / `DOORAY_SYNC_STATE_DIR=.dbg\ut\state` |
| 프로파일 | `utA`(검증 대상 PC 역할) ↔ `utB`(다른 PC 역할) — 상태 DB 분리 |
| 로컬 | `.dbg\ut\A` / `.dbg\ut\B` |
| 원격 | `_usertest` (신규 생성, 종료 시 휴지통) |

매 단계 `--dry-run`으로 **`실제로 사라질 항목`이 예상과 같은지** 확인한 뒤에만 실행했다.
판정은 라벨 존재가 아니라 **값**으로 했다(교훈 §5). 각 시나리오 마지막에 **연속 재실행 →
`변경 없음`**(수렴)을 확인했다(교훈 §23).

## 3. 발견 결함과 수정 (전부 수정 완료, 회귀 테스트 포함)

### 결함 #1 — reconcile이 "pull이 안내한 바로 그 상태"를 못 봄 (UT-04)

- 증상: init 이후 원격에 새로 생긴 파일이 로컬에도 있으면 pull은 `기준선 없음 —
  'dsync reconcile'로 대조하세요`라고 안내하지만, reconcile은 **DB 레코드가 있는 파일만**
  대조해 `대조 대상 0건`으로 끝난다. 안내를 따라도 영구 루프.
- 수정: DB에 없는 로컬 파일은 **원격 walk로 상대를 찾아** 대조하도록 보강
  ([cli/main.py](../dooray_sync/cli/main.py) reconcile). 원격에 상대가 없으면 push 몫으로 안내.
- 회귀: `test_reconcile_finds_remote_counterpart_missing_from_db`. 실계정 재검증:
  `내용 동일(기준선 기록) 1건`, 이후 pull 정상.

### 결함 #2 — dotfile 충돌 사본이 앞공백 이름 (UT-10)

- 증상: `.gitignore` 충돌 사본이 ` (충돌 ….).gitignore` — 앞공백 이름. 서버가 공백을
  절삭(R14)해 저장명이 어긋나고, 다음 sync가 개명 왕복을 한 번 더 돈다(file_id 이동
  감지로 자가 치유는 되지만 규약 위반 + 원본 정체 소실).
- 수정: stem이 비는 이름은 태그를 **끝에** 붙임 → `.gitignore (충돌 …)`
  ([core/differ.py](../dooray_sync/core/differ.py) `conflict_copy_name`).
- 회귀: `test_conflict_copy_name_format`에 dotfile + `name_issue`/`server_name_will_differ`
  불변식 검사 추가.

### 결함 #3 — 원격 이동 + 로컬 수정(C13)의 3중 문제 (UT-12)

- 증상 (실계정에서 확인): 보호로 옛 레코드가 남으면 이동 감지가 매 패스 재발동해
  **새 경로를 무한 재수신**(대용량이면 매번 전체 다운로드). 부수적으로 (a) 원격이
  '자리만' 옮긴 흔한 경우(웹 폴더 개명)에도 편집본을 영구 보호로 세워 두고,
  (b) `local_move`가 '이동 후 실측 stat + 옛 해시'를 섞어 기록해 편집된 파일을
  이동시키면 **편집이 영원히 안 올라가는 반쪽 기준선**(I4 위반)이 될 수 있었다.
- 수정 3건:
  1. 새 키에 같은 file_id 레코드가 이미 있으면(이동 실현 완료) 이동으로 재처리하지
     않음 — 옛 경로의 편집본은 결정표 10(보존 승리)으로 올라가 수렴.
  2. 원격 내용이 불변이면 편집본을 **새 경로로 함께 이동**(다음 패스가 결정표 4로
     업로드). 3중 발산(이동+원격수정+로컬수정)만 보호. 이동 목적지에 로컬 파일이
     이미 있으면 덮지 않고 보고.
  3. `local_move`가 기준선 세 값(mtime/size/md5)을 옛 값 그대로 옮김.
- 회귀: `test_case_13_pure_move_carries_local_edit_along`,
  `test_remote_move_already_applied_is_not_reprocessed`,
  `test_local_move_of_edited_file_keeps_old_baseline`.
- 실계정 재검증: 재수신 루프 소멸, 편집본 1회 업로드 후 양쪽 `변경 없음` 수렴.

### 관찰 (결함 아님, 기록)

- 폴더 개명이 로컬발일 때는 `원격폴더생성 + 파일별 원격이동`으로 분해되고 빈 옛
  폴더가 원격에 남는다(삭제 전파 꺼짐 기본값 때문 — 보고됨). 전파를 켜면 정리된다.
- C13 보호 후 편집본은 **옛 경로의 별도 파일**로 보존·업로드된다(트리 분리).
  Dropbox/Syncthing도 같은 상황에서 트리 분리가 나며, 유실이 없고 눈에 보이므로 수용.
- 소기준선(<20 레코드)에서는 비율 게이트가 면제된다(2026-08-03 설계 결정). 절대
  임계 50건은 항상 유효.

## 4. 재현 절차 (요약)

준비:

```powershell
cd C:\drive\dev\dooraydrive
$env:DOORAY_SYNC_CONFIG_DIR = "C:\drive\dev\dooraydrive\.dbg\ut\cfg"
$env:DOORAY_SYNC_STATE_DIR  = "C:\drive\dev\dooraydrive\.dbg\ut\state"
python -m dooray_sync.cli.main init -p utA --drive-id (드라이브id) --local-root ...\.dbg\ut\A --remote-path "_usertest" --create-remote
python -m dooray_sync.cli.main init -p utB --drive-id (드라이브id) --local-root ...\.dbg\ut\B --remote-path "_usertest"
```

각 시나리오는 §2의 표 순서대로: 파일 조작 → `--dry-run`으로 숫자 확인 → 실행 →
**재실행해서 `변경 없음` 확인**. 원격만 변경된 상황은 상대 프로파일(utB↔utA)의
sync/push로 만든다(웹 UI 불필요).

정리:

```powershell
python tools\trash_remote.py _usertest     # 원격 시험 폴더를 휴지통으로
Remove-Item -Recurse -Force C:\drive\dev\dooraydrive\.dbg\ut
```
